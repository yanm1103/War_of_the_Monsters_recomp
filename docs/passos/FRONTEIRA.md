# Hardware boundary: what of the PS2 the port no longer emulates

(Doc index in `CLAUDE.md`.) The game executable (`wotm.exe`) has no emulator code: no VU1, VIF0, VIF1 or GS on the CPU, no IOP interpreter or RAM, no emulated PS2 scheduler or EE timers. The recompiled game is still the base; whatever talks to the hardware is replaced at the engine boundary (the game's call, not the register). The emulated parts live only in the test executable (`ps2EntryRunner.exe`), as the **reference** for the VU1 x native check (`VU1CHECK.md`).

The static list (per TU: SDK calls, registers, COP2, scratchpad, 989snd) is `config/hw_boundary.csv` (`tools/hw_boundary.py`); the hardware functions are in `config/hw_funcs.txt`. This file is the **dynamic** view: what runs per frame in the live game and how each part is served.

## How to measure
- Run a fight with `PS2X_COVERAGE=<pasta>\cov` (the runtime writes `cov.<quadro>` every 300 screen frames, accumulated count per address) and, for a match without the menu, `WOTM_MATCH=3,1,1 WOTM_AIVSAI=1`.
- `python tools/hw_frame.py <pasta>\cov.1800 <pasta>\cov.4800` gives the per-frame calls of the hardware functions, per TU; `--modo sce` shows the SDK, libm and libgcc; `--modo tudo` shows everything.
- EE CPU cost: `WOTM_FIELDLOG=1` (`[field]` lines, `host - ocioso` per frame; `[stall]` with the game's pc when the EE goes three vblanks without reaching a checkpoint or waiting).

## Two executables (step 5)
The same build (`build_dev`) produces two executables from the same translated game objects (object library `ps2_game_code`, compiled once; CMake seam in `tools/runtime_patch/wotm-runtime.patch`). `ps2_runtime.h` is the same for both.
- **`wotm.exe`, the game:** links with `ps2_runtime_game` (`ps2_runtime` without the GS sources, `gs_frontend`, `gs_cpu_backend`, `ps2_gs_memory`, and without the VU1/VU0 interpreter, `ps2_vu1_core/upper/lower`, compiled with `PS2X_HW_EMU=0`) and with `ps2_iop_game`. The check, the photos and `--vu1cmp` are left out (`wotm_vu1check.inc` only warns). `wotm.map` has no symbol from `VU1Interpreter`, `GS`, the rasterizer, the check, nor from the IOP interpreter, kernel, imports or HLE modules (`mcserv`, `dbcman`, `libsd`).
- **`ps2EntryRunner.exe`, the test one:** emulated parts, `WOTM_VU1CHECK`, `WOTM_FOTOS`, `--vu1cmp`, corpus, full `EeScheduler.cpp`, emulated IOP.
- **Who runs which:** `run_live.ps1` uses `wotm.exe`, except with `WOTM_VU1CHECK` or `WOTM_FOTOS` on, with `-Exe test`, or when `wotm.exe` is missing or out of date (guinea pig); `run_live.bat` turns photos on by default, so it goes to the test one, and the launcher (photos off by default) goes to `wotm.exe`. `corpus.ps1`, `vu1cmp.ps1` and `live_attack.ps1` call `ps2EntryRunner.exe` directly; `lote.ps1` watches both (with `-Check 0` it runs the game one).

## How each part is served in `wotm.exe`
The step numbers (1 to 10) in the headings are the ones other docs and the code cite ("`FRONTEIRA.md`, step 4").

### Draw packets (step 3)
The frame packet reads are hooks on the call that builds them: text (font hooks, `wotm::FontText`), `ScreenPolys` HUD (hook on `polyBuildPrim`, `wotm::screenPolyFromCall`), lens flare (`Particles::readFlares`: the center and count that `lensFlarePacketBuild` writes in q44 come from `viewDef` and `lensFlareIndex`; the list is game state and the tables of the 18 sprites come from `lensFlarePacketInit`, which runs once), fades and menu bars (from the arguments of `rtFadeScreen(vista, quanto)`, `uiFadeScreen(quanto)`, `letterboxDmaData(alfa)` and `Shell::FadeScreen`, and from the `TheGame` level on return from `updateFadeOut`/`updateFadeOutAndIn`). Only the replay (`--vu1cmp`) reads the packets from the snapshot.

**The builders are not cut (returning early outside the check frame), on purpose.** Building costs about 0.2 ms of the EE's ~6 ms (`pktAddVu1ObjAsm` 130 to 165 µs over ~200 calls, `pktLinkAlphaObjAsm` 6 µs, `spritePacketBuild`/`texSpritePacketBuild` ~5 µs, `psBldBlockerPkt`/`psEndBlkObjs`/`psFindActiveBlockers` ~10 µs, `fontSpritePrint` 8 µs; for comparison, `hier` ~1 ms and `TheGame::Update` ~0.7 ms). The packets stay in RAM as game data and their DMA is discarded, so they do not tie the executable to the emulators. `pktAddVu1ObjAsm` is hand-written assembly with its own convention (it reads `$s0`/`$s5`/`$s3` and `vf*` from `hierTraverseAsm` and returns state in the context in `$s0`): returning early requires redoing what it leaves in the context, a big risk for 3% of the frame. **`hierTraverseAsm` cannot go away entirely**: it also animates, runs the control nodes, camera, light, particles, bones (the palette the native layer reads), locators and LOD.

### VU1, VIF1 and GS (step 5)
`PS2Runtime` has no `m_gs`, `m_vu0` or `m_vu1` (the VU0 state of the translated microprograms lives in a `VU1State`); the VIF1 does not exist (the channel 1 DMA walks the tags and completes without copying or processing the packets); the GIF arbiter has no packet function (the GIF channel completes and the packet is discarded, with no GIF chain shortcut to VRAM); `sceGsExecStoreImage` returns black (one call at boot, 4x4 Z32); presentation has no GS frame (black background, with the native scene and movies on top); `PS2X_NO_VU1/VIF1/GS` are always on from `main.cpp`.

### VIF0 (step 7)
The VIF0 only receives MPG, always the same fixed chain from the ELF (two MPGs of ~1.5 KB, the entire VU0 code memory), sent by `hierInit` at boot and by `hierLoadVu0Ucode` every frame; no UNPACK (shadows and particles do not use the VIF0). `tools/vu0native.py` writes into the `.gen.inc` the 4096-byte image that this chain leaves (`wotmVu0CodeImage()`), and in `wotm.exe` two hooks (`wotm_live.inc`, `wotmVu0UcodeInstall`) copy it straight into the code memory: `hierLoadVu0Ucode` becomes only the copy (which does nothing if the memory is already the same), and `hierInit` runs the original and copies right after, because the microprograms run before the first `hierLoadVu0Ucode` (without this second hook, the program at 0x430 runs 4 times with no code). `processVIF0Data` in `wotm.exe` is a no-op (seam in `ps2_vif1_interpreter.cpp`) and warns once if anything arrives; what arrives is a 48 B packet at boot that only sets STMASK and STCOL (only meaningful for UNPACK). In `ps2EntryRunner.exe` the VIF0 runs, and the hook only checks: on the second call of `hierLoadVu0Ucode` it logs `[vu0] microcodigo do VIF0 igual a a imagem gerada`.

### IOP (steps 1, 2, 6 and 9)
`ps2_iop_game` has only the PS2 paths (`ps2_path.cpp`, which the VFS uses) and another implementation of `IopSubsystem` (`ps2xIOP/src/iop_subsystem_host.cpp`): RPC with no server, module loading that fails, and no RAM or heap (allocate, free, read, write and range check fail, with the warning `[iop] memoria do IOP pedida (...)` the first 4 times). The 2 MB `iop_ram` of `PS2Memory` (`ps2_memory.cpp`) is not allocated in `wotm.exe` either (it has no reader in either executable).

Only the game's own movie decoder reaches IOP memory (per the `jal` graph): `sceSifAllocIopHeap` has only `strFileOpen` as caller (from `CMovie::Play` and from `initAll` of `MpegMovie`), `sceSifFreeIopHeap` only `strFileClose`, and `sendToIOP` (movie audio) sends through `sceSifSetDma`. The other SIF paths that reach `SetDma` (pad vibration, RPC, `sceSifResetIop`) are runtime stubs that do not touch IOP memory. That is why native movies are the default in `wotm.exe` (`main.cpp`: without `PS2X_FMV`, `PS2X_SKIP_MOVIES` or `PS2X_SKIP_CMOVIE`, it turns on `PS2X_FMV=1`): without them, the game's `intro_m` allocates 160 KB on the IOP heap and the decoder waits for the IPU, and the game does not get past the opening.

### What the game uses from the scheduler (step 8)
- **A single thread:** the main one (entry 0x100008), from boot to the fight (the movies, which would create threads, are native). No `WaitSema`/`SignalSema` (2 semaphores are created and never used), `SleepThread`/`WakeupThread`, event flag or alarm.
- **No INTC handler registered:** the vblank (causes 2 and 3) only writes the tick, the CSR field bit and the vsync flag, and wakes `sceGsSyncV`. **One DMAC handler**, the one from `hierSetDmaIntHandler`, called ~1 time per frame (end of the channel 1 DMA). Channel 2 (GIF) finishes ~5 times per frame without a handler.
- **Timers:** only T1, ~2 reads and 3 writes of the count per frame (`timer1Handler`, `timerWaitForMinUpdateRate`) and the mode in `timerInit`; no timer interrupt. T1 only feeds the base of the original `timerGetCurTics` (`D_006F8DC4`), which the replacement does not read. `timerGetFieldCount`/`timerGetUpdateRate`/`timerGetFieldsLastFrame` only read what `timer1Handler` (which adds the fields by host time, counted on entry, because the resume after `sceGsSyncV` does not go through the wrapper) and `timerWaitForMinUpdateRate` write, so they follow the host (`NATIVO.md`, "Timer from the host clock").
- **Per frame:** 27 to 47 thousand checkpoints of the generated code.

### Scheduler (steps 8 and 10)
`wotm.exe` compiles another implementation of the same class (`ps2xRuntime/src/lib/Kernel/EeSchedulerGame.cpp`, instead of `EeScheduler.cpp`; the header and the game code are the same, with new methods):
- **The main thread runs directly.** There is no ready queue, time slice or thread switch. The generated code's checkpoint only adds up the cycles and checks an attention flag, without reading the clock. The cycles do not advance EE timers or the IOP, and the GIF FQC does not rise (`ps2_memory.cpp`: the packet is discarded on the spot). `WOTM_TIMER_EMU=1` is ignored in `wotm.exe` with a warning (in `ps2EntryRunner.exe` it goes back to the emulated timer 1, which runs at ~1/3 of real time because the cycles do not follow the clock).
- **The vblank comes from a host thread** on the 16.667 ms grid, restarted from now after a stall of more than 4 vblanks (instead of firing the late ones all at once). The EE applies it at the next checkpoint or wait: tick, CSR field bit, `SetVSyncFlag` flag and tick, `sceGsSyncVCallback` callback, INTC causes 2 and 3 (no handler in WotM).
- **Waits in place.** `sceGsSyncV` (`WaitVSyncTick` in `Interrupt.cpp`, method `waitVSyncHere`) sleeps until the vblank and returns to the caller with the result in `$v0`, with no C++ exception. Semaphore, event flag, sleep and external wait also wait in place, serving vblanks and interrupts (WotM does not use them).
- **Interrupts and callbacks run nested**, with each depth's own stack (the DMAC handler is delivered at the checkpoint after the end of the DMA). What the header declares `[[noreturn]]` (`invokeCurrent`, `waitVSync` with continuation, `waitExternal`, `exitCurrent`) does the work in place and then throws the `EeDispatcherTransfer` exception, because the callers (RPC, syscall override, `ExitThread`, CD stream) rely on it; none of these paths runs in WotM.
- **Other threads do not exist.** `CreateThread` registers, `StartThread` fails, and so does `SetAlarm`, with the warning `[ee] ... nao suportado no wotm`.
- The `[stall]` of `WOTM_FIELDLOG` comes from the vblank thread, with the pc of the last call.

### Clock and vsync (step 4)
The game timer reads the host clock in both executables: `timerGetCurTics` replaced entirely, and `timer1Handler` adds the fields by host time ("Timers" bullet above). In `wotm.exe` the vblank is the scheduler's host thread. In `ps2EntryRunner.exe`, `EeScheduler.cpp` expires deadlines only by the host: `processDueDeadlines` removes the events whose `hostDeadline` has passed, the checkpoint checks the nearest host deadline every 16 calls, and idle (`waitForEvent`) waits for the deadline on the host and adds the stopped time to the cycles; after a stall of more than 4 vblanks the grid restarts from now. There the EE timers count by cycles. Test with frames of 1 and 2 fields: `WOTM_LOGICDELAY=25` (frames land on the grid, 16.7 and 33.3 ms, at 100% of real time).

## Open
- **Intermittent stall:** sometimes, in 4-monster fights (`WOTM_MATCH=3,1,2,5,1`), pauses of 0.15 to 1.2 s with little CPU and little idle (the EE thread blocked outside the scheduler; `[stall]` in `rtMain`, `inputUpdate`, `RtLoopView::startFrame`, `scePadGetState`, function entries without a native hook). With the host sampler (`PS2X_HOSTPROF`) on it does not show up. The `[stall]` of 44 to 150 ms while loading the stage (`Shell::LoadMonstersDB`, `fileReads`, progress bar) are expected. The tests run with the window minimized (`-WindowStyle Minimized`); worth checking whether the stall goes away with the window visible. Related to physics with `dt` and to `WOTM_RATEMIN`.
- Without "load settings" or "load game" in the session, "accept and save settings" only applies the options and returns to the menu, without saving. It is the game's behavior (same in the test executable).

**What is still PS2 in `wotm.exe`:** the draw packet the game builds in RAM, which is engine port work and not boundary work. The privileged GS registers (CSR, IMR, DISPFB) remain only as values that the SDK stubs read and write: nothing runs through them, and `sceGsSyncV` waits for the host vblank, not the CSR. **The hardware boundary is closed**; what comes next is in the root `TODO.md`.
