# Testing the new C++ in PCSX2 (halfcpp) and bugs found

(Doc index in `CLAUDE.md`.) halfcpp is the first way the equivalents were run; the planned path is the guinea-pig runtime (`PLANO.md`, "How a mod works", incomplete). What stays here is how to build the ELF and the lessons.

## How to build and run halfcpp
- The ROM of the normal build is identical to the retail (equivalents stay as `INCLUDE_ASM`). `sh tools/wsl/build_nm.sh` (WSL) compiles a copy in `~/wotm_nm` with `-DNON_MATCHING` and writes `build/pcsx2_test/SCUS_971.97_halfcpp.elf` (all the equivalents) and `..._control_matching.elf` (control). Both with `p_paddr = p_vaddr` (PCSX2 loads by `p_paddr`). Variants with a subset of TUs/functions: arguments of `build_nm.sh` (e.g.: `a_update` with only `Monster::update`).
- Running: `pcsx2-qt.exe -elf build\pcsx2_test\SCUS_971.97_halfcpp.elf -- "ISO\...iso"`; automated: `powershell tools/pcsx2_auto/play.ps1 halfcpp 60` (swaps the bindings to keyboard, plays the menu up to the stage, watches the log and restores the `.ini` with `emu.ps1 stop`; `-pause` presses START and photographs the dialog; `play.ps1 <elf> <n> <arquivo>` records the RAM). The PCSX2 log is in `~/Documents/PCSX2/logs/emulog.txt`: `Unrecognized op`/`executing data` = jumped into data; `Vif0: Unknown VifCmd` = wrong data; errors in a dialog show up as `ReportErrorAsync`.
- **Layout** (`tools/gen_nm_ld.py`): the normal linker script stacks the pieces, and any equivalent of a different size shifts the following data (misaligned DMA buffers, which is what broke the first test). The generated script pins every piece that did not grow at the retail address and sends the ones that grew to `.nm_extra`, after the bss. Limit: it pins only the start of each piece; raw addresses into a shifted piece are wrong (`undefined_*_nm.txt` relative to the symbol; `nm_fix_data.py` for function tables in `.short`; see "Guinea-pig runtime").
- **Heap**: `.nm_extra` would sit right after the bss, where the game's heap starts, and after a stage loads the whole RAM is in use (DMA overwrote the start of `takeHit`; symptom `executing data`). `patch_paddr.py --heap` (called by `build_nm.sh`) pushes the heap start past `.nm_extra` in two places: the crt0 `SetupHeap` call and `heap_ptr` of `libkernl/glue.data` (0x6E5D2C). `NM_HEAP=0x8E0000` puts the heap in the same place in both builds, so `ramdiff.py` can compare addresses.
- `CrushLevel` and `Monster` are compiled with `-G0` in the NM build (the strings of the new code do not fit in `.sdata`). `hierDmaHandler` needs the `hierFlushObjQ` prototype in `hieri.cpp` when only it is `NON_MATCHING`.
- The full halfcpp enters the stage and runs a whole match ("AI WINS"). If a variant hangs with "executing data", compare the EE RAM with the ELF before suspecting the function (rule in `CLAUDE.md`).

## Behavior bugs found playing halfcpp
Symptoms from the owner's test: ground vehicles without the green glow and ◯ does not grab; pedestrians walking in single file; some buildings can be walked through. Causes, reading the equivalents against the asm:
- **`PathNode` had 0x40 bytes, the retail uses 0x30** (4-byte links from 0x12, there are 7 and not 9): `PathNet::getRandNode/getClosestNode` indexed the wrong nodes -> pedestrians (and cars, which follow the PathNet) in single file. There is a `typedef char PathNodeSizeCheck[...]`.
- `AiBrain`: the empty base class `AiActionGroup` takes 1 byte in gcc 2.95 and pushed `f_AAC` to 0xAB0 (retail 0xAAC). No inheritance there.
- `AiGrappleAttack::updateAction`: with `matchMode` 0/1 the retail picks `heavyPunch` (ours called `toss`). Found by `tools/nm_calls.py`.
- `Monster::isIdle`: last test inverted (the retail returns 1 when `t < state[2]`); only the camera uses it.
- **`Interactives::addInteractive` written as `void`**, but the retail callers (`CarPickup::initAfterDbLoad`, `HeliPickup`, `Destructible`...) use `$v0` (the slot index) as the id in the `hierhead`. The leftover `$v0` was index+1, so every `getInteractive(idx)` returned the neighbor: it breaks `getClosestPickup` (glow and ◯), the returned ball and the continuous damage on buildings. `tools/nm_retvals.py` sweeps the `void` equivalents with a consumed return.
- `Monster::update`: `sb` at `m_x6874+0xC` and `f5C` as a byte.
- **Lesson:** "untuned" with many differing words can hide a layout/semantic error, and the difftest caught none of these (random state, stubbed callees). Hence `nm_audit.py` (offsets and immediates, NM ELF x retail), `nm_calls.py` (call sequence), `nm_retvals.py` and `ramdiff.py` (two EE RAM dumps at the same point: equal pickup lists, `Interactives`, `ColGrid` and pools = right level setup, dynamic defect). All of this runs together in `tools/verify_tu.py`.
- How to find a defect of this kind again: a RAM dump with the game paused (`ramdump.py`), and a draft script that reproduces the retail computation from the dump (that is how `getClosestPickup` was found).
- difftest with structured state: `--init '<python>'` (W/W16/W8/THIS/ARENA/STUB); `Monster::update` needs `m_state` with a vtable and still falls into writes outside the map.
