# Native layer (native/): drawing, textures, characters

(Docs index in `CLAUDE.md`.) This file keeps **what is known**, not the investigation diary. The full account (discarded hypotheses, intermediate measurements) is in the previous version: `git show 01050d2:docs/passos/NATIVO.md`.

## Overview, files and flow
The scene is read straight from the EE RAM and drawn with raylib, without VU1/GS, with the game's camera. Files:
- `native/wotm_native.hpp` (single header: `Ram`, matrices, `decodeObject` = mesh from the `polyPkt`, `Scene::collect/draw`, camera), `wotm_gs.hpp` (GS addressing, textures), `wotm_fx.hpp` (particles), `wotm_fmv.hpp` (movies), `wotm_snd.hpp` (sound), `viewer.cpp` (standalone viewer: free/game camera, `--shot`, `--texdump`, `--lod n`, `--cam`, `--disc`, `--rtx`), `fmvplay.cpp`, `build.bat` (MSVC; raylib from the runtime clone). Formats in `docs/FORMATOS.md`; offline mesh reader in `tools/ngp.py` (`TRACE` shows MSCAL/MSCNT per sub-packet).
- **Offline iteration (seconds):** the runtime writes `ram_<q>.bin` + `vram_<q>.bin` (`PS2X_DUMP_RAM="3300,3900"`) and `build\viewer.exe ram_<q>.bin` draws it. Dump of a running runtime: `python tools/pcsx2_auto/ramdump.py <discroot>/SCUS_971.97 saida.bin ps2EntryRunner` (the same script reads retail PCSX2).
- **Live:** `PS2X_SCENE=1` (with `PS2X_NO_VU1=1 PS2X_NO_VIF1=1 PS2X_NO_GS=1`) draws into a 4:3 render texture on top of the GS frame (`wotm_live.inc` -> `wotmDrawNative`); with no stage loaded the GS frame stays. Run: `run_live.ps1` in the `wotm-recomp-win` clone (`-Auto 0` to play, `-Stats 1` logs `[native]`), or `WotM_Launcher.exe`. Keys: **F3** FPS counter (off at startup), **F11** toggles fullscreen and window, **F1** debug menu (cheats; section "Runtime: debug menu (F1) and cheats").
- **Rebuilding the runtime after touching `native/`:** `build_runtime.bat` at the root (or `tools/build_runtime.ps1`). Ninja **does not track** `native/*.hpp` or `native/runtime/*.inc` (they sit outside the PS2Recomp tree): the script touches `ps2_runtime.cpp`; without that it reports "no work to do" and the game keeps the old drawing.
- **Addresses by name:** `native/wotm_syms.h`, generated by `python tools/native_syms.py --gen` from `symbol_addrs.txt`, gives `wotm::sym::<dado>` and `wotm::fn::<função>` for the 7,282 symbols of the ELF (gcc 2.95 names with `$`/`.` replaced by `_`; names that start with `_` or clash with an MSVC macro get an `x` prefix). In new code, use the name, not the number; `--audit` lists what is still raw in `native/` (28 literals remain that are fields inside a symbol, whose right name is the one from the types header, and ~40 that have no symbol: bss `D_*`, masks, VRAM addresses) and `--apply` replaces the exact ones. Regenerate the header when `symbol_addrs.txt` changes.
- **Where the runtime code lives:** the hooks and the game-specific code that run inside the runtime are in **`native/runtime/`** in the repo: `wotm_live.inc` (live drawing, boot trace, watchdog, movies; includes `wotm_snd.inc`, `wotm_pad.inc` and `wotm_padsel.inc`: per-player controls and side selection), `wotm_scene.inc` (entry point included by `ps2_runtime.cpp`; includes `wotm_vu1check.inc`), `wotm_vu1check.inc` (VU1 x native check, snapshot and `--vu1cmp`), `wotm_overrides.cpp` (game clock, `WOTM_MATCH`, `AIVSAI`...) and `wotm_vu0_native.cpp/.h` (dispatch of the VU0 microprograms; the translated `.gen.inc` goes to `<build>\wotm_gen`, outside the repo) and `wotm_standalone.cpp` (`wotm.exe` with no argument: first run, folders and log; `RUNTIME.md`). The fork's CMake (`-DWOTM_NATIVE_DIR=<repo>/native`, required) includes `native/` and `native/runtime/` and compiles the three `.cpp` files. The patch `tools/runtime_patch/wotm-runtime.patch` holds only the PS2Recomp seams (CMake, `main.cpp`, taps on VIF1/VU1/memory, scheduler, pad, profile). A change in `native/runtime/` is a normal commit in the repo; a change in a seam requires regenerating the patch.
- **Stage change (`levelSignature`):** a hash of only the header of the level image at 0xA00000 (N + N pointers) and of `tempVramTexAddr`. The whole first KB does not work: it includes live nodes (the menu rewrites floats at +0x3E0..+0x3F8 during transitions), and with it the scene would be invalidated every frame (~870 meshes and ~80 textures reloaded, 50–70 ms drawing, screen at ~16/s during menu transitions). Diagnostics: `WOTM_CAMLOG=1` (one `[cam]` per draw).
- **Without VU1 nobody completes the packet:** the game waits for `objsInPacket | objsInAlphaPacket` (0x6F87A0/A4) to reach zero in `rtWaitForVu1` (hooked) and in a loop embedded in `particleDraw` (0x21B8A0); with `PS2X_NO_VU1` the presentation (60 Hz) zeroes both. Old experiment variables: `PS2X_GS_UPLOADS`, `PS2X_VIF1_UPLOADS`, `PS2X_NO_VU1=2` (no longer needed).

## Textures and palettes
- **Pixels:** `texInfo[texId]` (0x50F100, 16 B per entry) points to a packet: width `+0x24`, height `+0x26`, TBW `+0x2A`, PSM `+0x2B`, **linear** pixels starting at `+0x80` (T8 = 1 byte, T4 = 2 per byte, low nibble first). The object's TEX0 `TBP0` is usually 0 (`texm` patches it at draw time) and is not used.
- **Palettes come from the disc `.RTX`**, never from the dump's VRAM (which holds menu leftovers). Entries of `(palavra0 >> 2) * 16` bytes, 16 B header (GS descriptor at `+8`: relative DBP in the halfword `+0xA`, TW/TH in bits 40..47); 16x16 CT32 = 256 colors (1040 B), 8x2 = 16 colors (80 B). `Scene::loadResources(ram, raiz)` indexes by **absolute CBP** (`rtxPal`); it is idempotent.
- **Base of each `.RTX`:** the game stacks level, players and AIs in load order; `fileStatus` (0x445390) holds `names[i][9]` (+0xB1) and `maxTexAddr[i]` (u16, +0x14C). Level base = `tempVramTexAddr (0x6F8818) >> 6`; base of file `i` = `maxTexAddr[i-1]`. Search: `LVL/<nome>.RTX`, `MON/<nome>.RTX`, `<nome>/<nome>.RTX` (menu: `SHELL/SHELL.RTX`) and `SHELL/<nome>.RTX` (LOAD, UI, SHELL2, PRESHELL).
- **CSM1:** 256-color CLUTs have bits 3 and 4 of the index swapped; logical entry `i` = word `(i & 0xE7) | ((i & 8) << 1) | ((i & 0x10) >> 1)`. Only in T8/T8H (without it: grainy portraits and monsters, without the yellow spikes).- **PSMT8H/4HL/4HH** (menu: screens, fonts, logos, 512x512 portraits): `texInfo` does not point to the right pixels; the pixels are in the `.RTX` (0x80 B header, psm in bits 32..37 of the desc, sizes `0x1080`, `0x880`, `0x40080`). `TEX0.TBP0 == DBP` of the entry; 4HL and 4HH share the DBP (the two nibbles of the same byte). Stored in `rtxImg[(psm<<16)|DBP]`. The entry with size 0 is the last one in the file and also counts (in the monsters, the HUD portrait); in the monsters the DBP is relative and adds `fileStatus.maxResAddr` (+0x168) of the previous file, as in `texmResRelocate`. Texture 180 (128x128, tbp0 4096) comes from a file not yet identified.
- **Alpha:** texture and vertex go **raw** (no `fixAlpha`, no ×4): the GS blends with As = At·Av/16384, and the `Scene::draw` shader does `3.969·t.a·v.a` (up to 255/128; in the common blend, As above 1 comes out in two extra passes, `gsBlendOver1/2` in `wotm_fx.hpp`) (CT24 and the CT16 bit give 0x80; sections without a texture use `gsWhiteTexture`, alpha 0x80). Measurement and captures in `a3973ff^:docs/passos/VU1CHECK.md`, "Escala do alfa". Object UV = `int16/4096` normalized by the size (as in retail; buildings go to ±8 and repeat on purpose; UV outside 0..1 requires `TEXTURE_WRAP_REPEAT`).

## Meshes and draw state
- **Point lights:** fire (breath, `Weapons::CreateFire`, `Monster::lightOnFire`) creates lights in `pointLights` (0x6DFCE0: 32 `PointLight` of 0x40, position +0x10, range +0x1C, color +0x20, falloff +0x2C = range²/(16·intensity), on at +0x38). In pass 1 the `hier` calls `GetClosestPts` (up to 8 enabled lights closest to the camera into VU0 memory; with `closest[0] < 0` the count is 0 and the rest of `closest[]` keeps old garbage). `hierTraverseAsm` calls VU0 program 0x748 for OBJECT with `pointLight` (0x80), `objType` 0 and, in a `_cs`, `ptLightMe` (+0xA9): with R = rows 0–2 of the matrix and T = row 3 minus the camera (camera-relative stack), v = Rᵀ(L − camera), it touches if |T + center − v|² < range² + radius², up to 3 lights, and sends T − v (q169–q171). With a light, `pktAddVu1ObjAsm` swaps the light program for 0x15D8 (before `dirLight`): color = min(255, color·q5 + Σ color_k·min(0.5; max(0, (L_k − p)·n)·falloff_k/|p − L_k|²)), n = normal/128, no directional light. `Scene::objectPointLights`/`pointRgb`; corpus snapshot `luz_pontual`; check dump with the `ptl` line (q169–q175); `WOTM_PTLOG`.
- **Vertex alpha:** almost everything has ~0x42 and is opaque; the VU1 sends it as is and the scale is the GS's (see "Alpha" above). The template's `PRIM.ABE` does not decide blending by itself; the shader does `discard` below ~6%.
- **ADC (STMASK + S-8):** skips only the triangle that ends at that vertex; the strip continues. Treating it as a restart loses triangles (holes, torn sky). `tools/ngp.py` still uses the old model.
- **Multitexture:** up to 5 textures per object (`texId[5]` at `+0x50`, `numTextures` `+0x5A`, `gsTexCtx[i]` at `+0x70 + 0x30*i`). The 4th word (high REGS) of each section's GIF tag is the **selector `1 + 3*slot`**, with two rules: `sel = 0` **inherits** the previous section's texture (the GS keeps TEX0; state in `MeshData.curSlot`, initially 0), and **bit 15** is a flag (slot = `(sel & 0x7FFF)`). Without this: terrace with a wall texture, "camouflaged" police cars (retail does not have these defects). Open, low risk: 1st section with `sel = 0` (only texId 189).
- **Blending:** the GS state of a translucent object comes from the **`ctx` of the nearest parent node that has one**: GROUP, TRANSLATE, ROTATE and SCALE at `+4`, ANIM_XFORM and ANIM_SCALE at `+8` (`Scene::CtxScope`); with none, `ctxGetDefaultGSCtx` (0x44). It is an A+D tag with `ALPHA_1` at `+0x20`, `TEST_1` and `ZBUF_1`. `0x44` = normal, `0x48` = additive (Kineticlops), `0x42` = `Cd - Cs*As`, `0x46` = `Cd*(1-As)` and `0x81` = `(Cd-Cs)*As` (Kineticlops in color 3). `Scene::groupState` reads the `ALPHA_1` byte (`DrawItem::blend`; `gsBlend` in `wotm_fx.hpp` translates any `(A-B)*C+D` to GL factors) and the `TEST_1` threshold (`DrawItem::aref`, shader uniform `alphaRef`; default `kGsAlphaRef` = alpha > 8, the common `0x8D`; ATE 0 or ATST ALWAYS = no test, `kGsAlphaNoTest`). The frame goes to the window **without blending**: the framebuffer alpha is the blends' alpha, not opacity. **Order:** outside the alpha OT (bit `0x8000` of the flags), opaque and translucent objects come out in traversal order, writing Z according to the `ZMSK` of the inherited `ZBUF_1` (`DrawItem::zmsk`); the alpha OT comes after, by depth band and LIFO (`alphaBin`, `inAlphaOT`), and shadows last (`a3973ff^:docs/passos/VU1CHECK.md`, "Ordem do hier e OT de alfa"). `hierTraverseAsm` writes the current ctx into every object of the alpha OT, so the state does not leak from one object to the next (the explosion sphere's ctx comes from a TRANSLATE/ANIM, not from a GROUP; reading only GROUP it comes out with 0x44).
- **zBufferFudge** (`HierObject +0x28`, 1.0..1.12): **>1 = closer** (in the GS a larger z is closer and z ~ 1/distance); the native layer scales the vertex along the eye ray by `1/fz`. With the wrong direction, labels of the options menu, lit windows and dirt trails disappear.
- **Sky:** `worldCtx[0]` `+4/+8/+0xC` (`skyCs`, `skyCs2`, clouds), before the world, without depth, at `skyCs->trans` like `hierTraceSky` (not at the eye). `trans` changes only through `viewSetSkyTrans`, which `hierSetCamera` calls after the traversal passes a camera node: in the menus that is every frame (trans = eye), in the fight the sky stays where the last locator camera left it and the game camera moves around it (parallax of the mountain ring, `tex 108`; drawing the sky at the eye loses this parallax). It is part of the check's triangle comparison. **HUD:** ids 0x1C20..0x2133 (except button icons, below) are `hier` objects that the game places in front of the camera every frame (`Hud::update`, `Letterboxing::update`); they go to `Scene::hud`, drawn last, without depth (details in `VU1CHECK.md`, "Fixed"). The HUD that comes out as a GS packet through `ScreenPolys` (the health marker of the other monsters) is read at the entry of `ScreenPolys::dmaData` (`wotm::readScreenPolys`) and drawn like the text, before it (`VU1CHECK.md`, "Fixed"); `Hud::dmaPacket` exists only with split screen, which the native layer does not have.

## Hierarchy, LOD and characters
- **Rigid:** `CHAR_INSTANCE` (`+4` = `animOutput.val`, `+0xC` = `atMat`, `+0x14` = `animMatrixPtr`, `+0x18` = `animPktPtr`, children at `+0x2C`). `ANIM_XFORM` (op 17): the game computes the local matrix in `atMat[matrixIdx]` (`+0xC4`; `visible` float `+0xC`, children `+0xCC`); the native layer only reads it.
- **Op 35:** container of `ANIM_XFORM` (count `+4`, children `+0xC`) with the monsters' **rigid parts** (hands, claws, head, thruster). Ignoring it removed Robo-47's hands and head and Togera's blades.
- **`ANIM_SCALE` (op 38):** visibility is `val[vidx]` (`vidx` int16 at `+0x10`): 0 skips the node and its children, `-1` = always. `+0xC` is static (reading it kept Robo-47's blades and flame always visible).
- **`DESTRUCTIBLE` (op 39):** descends only into `child[whichChild].child`, with `whichChild` = `INTERACTIVE_STATE +4` of the parent. Validated in a match with attacks (building in ruins). Missing: dust/fire/`Debris` and the `actions` of the state change. `WOTM_DESTRSTAT=1` counts per state.
- **`CONTROL` (op 8, "ghost" building):** `+4` solid, `+8` ghost version (or null = disappears), `+0xC numVolumes`, `+0xE volType`, sphere `+0x10/+0x1C`, BSP volumes at `+0x20` (leaf `0x200` = air). `volType == 0`: eye outside the air -> child2. `volType != 0`: segment eye -> aim point (`g_cameraLosPoints` 0x50F020, direction in xyz and distance in w; count at 0x50F0C0) crossing a solid leaf -> child2. `Scene::ctrlChild` reimplements it (the original `bspVecTestIn` is asm); only view 0 and up to 2 points.
- **LOD:** picks the largest index whose `switchOutDis` (`+0x20 + 16*i + 4`, squared distance) is greater than the squared distance from the center (`+0x10`, transformed) to the eye; none -> not drawn. Index 0 is the coarsest. With the level's `fade`, the cross-fade is the one from `hierTraverseAsm` (level i - 1 before i; `DrawItem::fade` and `lodX` take both to the alpha OT).
- **Skinned (monsters):** `CS` 96/97/101/105/106/107 -> GROUP -> `CHAR_INSTANCE` -> `SKEL_BONE` + `LOD`. The `polyPkt` is a **chain of sub-packets**: tag `0x600100b4` (bit 16 = skinned; the low 16 bits are not a size), `UNPACK V4-32 @0xB5` (up to 190 vertices: xyz + weight in w, **bone code in the low 8 bits of x, y and z**), normals `V3-8 @0x175`, strip sections; each sub-packet ends in two NOPs and the next comes qword-aligned after zeros.
- **Matrix palette:** `animPktPtr[OBJECT+0x68]` (the OBJECT's own index, as in `pktAddVu1ObjAsm`; negative = no palette, the game sends the packet at `+4`. It is not the LOD index: the Dragon has body and wings in the same LOD, at 5 and 6) -> 1st tag `3000007d <endereço>` -> block of 125 qwords (the Dragon's body uses its own palette of `0x41` qwords, 16 matrices, for the same VU1 address); bone code = qword address in the VU1: `slot = (código & 0x7F) / 4`, matrix at `bloco + 0x10 + 0x40*slot`. `animMatrixPtr[i]` points to **shuffled** slots (do not use `animMatrixPtr[código/4]`). Bit 0x80 is not used by the microcode.
- **Weights (VU1 microcode disassembled with `tools/vu1dis.py`, output in `build/vu1/`, game code):** 3 bones per vertex, `w1 = w`, `w2 = frac(w * 2048)`, `w3 = 1 - w1 - w2`; position = `w1*Mx*p + w2*My*p + w3*Mz*p`. Implemented in `skinVertex`.
- **Robo-47:** the **electric arc** of the dome is the `fx[]` of visual type 7 (VisArc), `texLoad[0]` 57; drawn by `Particles::arcQuads` (97.5% matched with the VU1; `VU1CHECK.md`, "Electric arc").

## Physics with `dt = 1/updateRate` (runtime)
The game integrates several things by Euler with `dt = 1 / timerGetUpdateRate()` (0x2236D8). In retail the rate is 60 or 30; in the runtime it oscillated between 60 and 8 (vsyncs arrive in bursts: one game frame lasts 1 vsync, the next 6), and with a large `dt` the integrators diverge:
- **Congar's fur "exploding":** the 8 fur bones (4, 8, 11, 13, 20, 22, 26, 28) are **springs** (`BoneSpring::update`, 0x11B5C0: `Spring::applyForces` + `PointMass::resolveForcesEuler`). The offset of ~5 to 6 between `atMat.linha3` and `nó.t` in these bones is **normal** (same in retail). The spring is stable only with `dt²·k/m` below ~4. Ruled out by measurement: VU0 interpreter (15 million `vcallms` compared with the reference, `PS2X_VU0_VERIFY=1`), `vf0`, native layer.
- **Monster spinning by itself (camera along):** `MonsterDynamics::updatePosition` (0x165100) integrates `ang.z` with damping ≈ `-40,5·velRot`, stable only with rate ≥ 21; with rate 10 the velocity flips and grows. `WOTM_TURNLOG` prints `[turn]`.
- **Rate floor:** `timerGetUpdateRate` returns at least `WOTM_RATEMIN` (default 30; 0 disables) for the whole game (`wotm_overrides.cpp` in the runtime). On slow frames the game runs a little slower instead of skipping.
- **`particleDraw` wait:** the game measures the logic duration with timer 1 (`fields = ticks / 9619`, `updateRate = 60 / fields`). The `particleDraw` loop at 0x21B8A0 waits for `objsInPacket | objsInAlphaPacket` to reach zero (VU1 completion); without VU1, if only the presentation zeroed them, the loop would burn 32 virtual cycles per iteration and the game would measure 2 to 4 fields at random. That is why `main.cpp` (with `PS2X_NO_VU1`) and `EeScheduler::checkpointDue` zero the counters at the entry of `particleDraw` and do not count cycles in that loop.
- **Rate ceiling:** `timerWaitForMinUpdateRate` only waits one more vsync if the rate goes above the ceiling (`D_006F8DD8`, written by `timerInit`). With 1 and 2 players the ceiling is 60, and logic at 30 indicates runtime slowness. With 3 and 4 the game turns on "30 Hz mode" (`Shell::Use30HzMode`: `m_numPlayers >= 3`): `Shell::BootInitGame` calls `timerInit(30)` and `getVramAddr` switches the VRAM layout. The port changes only the `timerInit` at that point to 60 (`timerInit60` in `wotm_overrides.cpp`), and the logic with 3 and 4 players runs at 60 whenever it fits in 1 field; `WOTM_30HZ=1` restores the ceiling of 30.
- **Fields = vblanks of the frame (`wotm_overrides.cpp`):** the frame starts a few host ms after the vblank, so the logic can cross a vblank with timer 1 below 1 field, and the game would count 1 field in a 2-vsync frame (the game runs slower than the clock). At the entry of `timerWaitForMinUpdateRate` the field counter is at least the vblanks since the start of the frame (marked by the `timerGetCurTics` called at its end or in `timerSetFrameStart`). The `particleDraw` wait also zeroes the counters inside the loop itself (they go up inside it).
- **Timer from the host clock (`wotm_overrides.cpp`; `WOTM_TIMER_EMU=1` goes back to the emulated timer 1):** `timerGetCurTics` is replaced entirely and returns the host clock at the timer 1 frequency (576 kHz, BUSCLK/256, mode 0x82 of `timerInit`; 9619 ticks per field). `timer1Handler` keeps running, because it waits for the vsync, but the fields it adds (`ceil(T1 / 9619)`, up to 16) come from host time since the last zeroing of T1 (end of `timerWaitForMinUpdateRate`, `timerSetFrameStart` or the previous `timer1Handler`). The computation is done **at the entry** and the emulated T1 is zeroed so the original adds 0: `timer1Handler` almost always blocks in `sceGsSyncV`, and the resume goes straight into the middle of the recompiled function, without passing through the wrapper; an "after" in the wrapper does not run (this holds for any hook on a function that blocks). The rest of the timer (`timerSetFrameStart`, `timerEndOfRealTimeProcessing`, `timerGetFrameTime`, `timerGetAverageFrameTime`) only sees T1 through `timerGetCurTics`. The "fields = vblanks" rule still holds with the host clock: the delay between the vblank and the start of the frame (`wotmCaptureFrame` runs there) exists just the same. With both, game time follows real time (`WOTM_FIELDLOG`), also with 1- and 2-field frames (`WOTM_LOGICDELAY`).
- **Vsync from the host clock (`EeScheduler.cpp` in the patch):** every scheduler deadline (vblank, alarm) expires only by the wall clock; the virtual clock is not pulled to the wall clock and `waitForEvent` does not add delay. Virtual cycles are left for the EE timers and the time slice between threads; idle adds the time actually spent stopped. Measurement and what is still open in `FRONTEIRA.md`, step 4. Test with slow frames: `WOTM_LOGICDELAY`.
- **VU0:** the interpreter (`VU1Interpreter` with a pipeline model) costs ~3.9 µs per `vcallms` and gives the same result as the upstream one: it does not clear the 64 KB XGKICK buffer on every call, commits only the queues with something ready, has `normalizeOperand`/`broadcast` inline and decodes the pair by reference. The offline bench re-runs the `PS2X_DUMP_VU0` samples and compares with the upstream interpreter.
- **Native VU0:** `tools/vu0native.py` reads the VU0 microcode from the ELF (VIF packet with MPG at file offset 0x15C890) and generates C++ for the 14 microprograms the game calls. The generated `.inc` is a translation of game code and stays outside the repo: `build_runtime.ps1` generates it in `ps2xRuntime/src/lib/vu/` when it is missing or when the script changes. `wotm_vu0_native.cpp` dispatches by pc and uses the native version only if the FNV-1a hash of the program's range in code memory matches; the hash is recomputed when the code generation changes. `WOTM_VU0_INTERP=1` sends everything back to the interpreter, and `PS2X_VU0_VERIFY` and `PS2X_DUMP_VU0` also force it.
  - **Arithmetic:** the same as the interpreter, on all 4 lanes at once (SSE for float, AVX for double): normalized operands, float computation rounded toward zero and the result classified by its double value (zero, overflow, underflow), with the product sticky in madd/msub.
  - **Branches and flags:** the generator compiles blocks specialized by the pipeline state at entry (cycles left for each VF/VI/ACC to be ready, pending flags and where they are, VI saved for the following branch, `bal` return address). Stalls and the cycle in which each MAC/status flag becomes visible to `fmand`/`fsand` come from the state, without depending on the data. Branches become `goto`, and the 0x748 loop closes when the state repeats. 0x430 and 0x4D0 call the subroutine 0x598 (sine and cosine with flag branches) and become 13 blocks each.
  - **Verification:** the cycle model matches the interpreter on the 11 straight-line programs. The interpreter's 4096-cycle budget, which cuts the program in the middle, is not reproduced: the native version always runs to the end, like the hardware.
  - **Floating point:** the runtime compiles with `/fp:fast /arch:AVX2`, and with that the compiler fuses `acc + a*b` into an FMA, with a single rounding, while the VU rounds twice. The interpreter in the runtime, therefore, does not reproduce the VU bit for bit at this point. The native file compiles with `/fp:precise`, outside the unity batch.
  - **Bench:** in `vu0bench`, with the native version compiled as in the runtime, it is identical to the interpreter in `/fp:precise` over 840 thousand runs with perturbed inputs (extreme values, denormals, inf/nan, cancelling sums, random flags and VI), except those that exceed the budget. Against the samples recorded by the runtime there is a difference of 1 to 3 ulps, the same the interpreter in `/fp:precise` has with them.
  - **Gain:** 13× to 28× per call (0x0: 3.5 → 0.15 µs; 0x1A8: 8.5 → 0.53 µs; 0x4D0: 11 → 0.58 µs).
  - **Automatic fight in Centro (1 vs 1):** CPU per frame went from median 15.0 / p90 18.6 / p99 23.4 ms to 4.7 / 6.3 / 10.0 ms. Logic stays at 60 in 99.9% of frames (previously 82%).
- **4 monsters (match in Centro: Shogun, 2 Congar, Lizard):** CPU per frame median/p90/p99 of 6.2/7.8/10.0 ms (21.2/25.4/28.3 with the interpreter); logic at 60 in almost every frame; game time 97% of real time. **Open:** host stalls of 100 to 330 ms outside the fight; `_NLG_Return2` (~12%, MSVC stack unwinding).
- **Reading `[field]`:** it is printed at the entry of `timerWaitForMinUpdateRate` (every frame) and describes the previous frame (`timerGetUpdateRate` does not work: in the menu and at the start of the stage it is not called every frame, and the line would add two). `syncv=N:ra,...` counts the calls to `sceGsSyncV`.
- **Recursion in PS2Recomp:** a recursive function paused on the call to itself cannot be taken as finished, or the game jumps to garbage; the handling is in `dispatchGuestBranch` (`ps2_runtime.cpp`). If it happens, the `[resume]` log lists the last 64 resumes before the invalid pc.
- **Build:** the unity build does not recompile the batch that includes `main.cpp` when only that file changes; `tools/build_runtime.ps1` deletes that `.obj` by itself.

## Runtime: host hooks end with `pc = $ra`
Every hook of ours (sound, movies, `rtWaitForVu1`, `hierFlushObjQ`...) is registered with `hostLeaf<f>` (`ps2_runtime.h`): if the hook did not change `pc`, it does `pc = $ra`. Reason: when the time slice ends right on a call, the scheduler resumes by calling `lookupFunction(pc)`; recompiled functions and stubs end with `pc = $ra`, but a raw hook left `pc` at its own entry and was called forever (the logic froze while the drawing stayed live; seen with `pc = snd_FlushSoundCommands`). A new hook without `hostLeaf` brings the freeze back. **Calling game code inside a hook** (`callGuest` and equivalents, with `ra` 0): in `ps2EntryRunner.exe` the scheduler interrupts the recompiled function in the middle when there is a pending event (`checkpointDue`) and it returns with `pc` at the resume point, without having finished. Every such helper calls `wotmFinishGuestCall` (`native/runtime/wotm_guestcall.h`) right after, which follows `lookupFunction(pc)` until `pc` is 0. Without it the rest of the function is lost: the `viewSetFov` called by the co-op screen switch stopped before transposing the `ViewDef` planes, the view frustum was wrong and the monster, the health bar (which is a 3D object) and pieces of the stage disappeared depending on the angle. **Modal function:** the hooks' `callGuest` calls set `ra` 0; a game function that runs frames and yields to the scheduler (`displayDialog`) is resumed by the scheduler without the host stack, and at the end returns to `pc` 0: the main thread becomes `Dormant` and the game freezes (the runtime logs `[resume] thread N terminou em pc 0` with the last resumes). Rule: a game function that can wait for frames (dialogs, loads) does not go through `callGuest`; call it as a tail call (arguments in the registers, `pc` = the function, `ra` = the original caller's), like the end of round in `wotm_split4.inc`.

## Runtime: freeze and pace watchdog
On by default, in the presentation loop (`ps2_runtime.cpp`, next to `PS2X_DUMP_RAM`). `g_frame` (0x6F7E38) goes up on every frame of the fight (`rtMain`) and of the menu (`ShellRtLoop::endField`, which also covers the pause dialog). If it stays still for `WOTM_WATCHDOG` seconds (default 8; 0 disables) while the screen keeps drawing, the logic froze. A movie (`movieIsPlaying`, 0x6F8650) does not count. This fires once per stop: `[vigia] CONGELOU` lines with the EE threads (pc/ra to look up in `symbol_addrs.txt`) and the semaphores in `live.err.log`, plus `ram_vigia_<g_frame>.bin` and `vram_vigia_<g_frame>.bin` in the disc folder (`discroot`), which is the cwd. When the game moves again, `[vigia] g_frame voltou a andar` is printed. The measured legitimate stops (menu and stage loads: `zipBuildHuffmanTable`, `Shell::FadeScreen`) last 1.3 to 2.5 s. Pace: 2 s windows with the game running below `WOTM_MINFPS` frames/s (default 25) produce `[vigia] LENTO` and then `ritmo normal de novo` with the duration and the minimum, without a dump. Windows with a gap of more than 1 s between frames are loads and are left out.

## Runtime: debug menu (F1) and cheats
In the fight (only where native drawing runs), **F1** opens and closes the menu; with it open, **1** invincible, **2** stamina (normal, full, rage = 130), **3** special always ready, **4** CLOAK, **5** god mode (the game's own `m_godMode`, +0xE9: no damage, health, stamina and special full; plus, from us, no reaction to hits), **6** win the fight, **7** knock-down target (all players, P1..P4), **8** knock down (one shot: each living player of the target takes a `takeDamage` larger than their health, through the normal death path, and loses a life; useful to test life loss and exits in the co-op campaign). Arrows and Enter belong to the pad, hence the numbers. When closed, an orange reminder shows what is on. The window only writes `g_wotmCheats` (`native/wotm_cheats.h`); the EE thread applies it, at the entry of `Monster::update` of each player (`m_monsters[0 .. m_numPlayers-1]`, `wotm_overrides.cpp`), before that player's frame logic.
- **Invincible:** `Monster::takeDamage` returns at entry when the victim is a player, including with forced damage. The hit still pushes (the reaction comes from another path); only the health does not drop.
- **God mode without reaction:** on the player, `Monster::takeHit` (virtual entry of every hit), `knockBack` and `takeAdditiveRecoil` return at entry, and `enterNewState` refuses the reaction states (Recoil, KnockBack, Grappled, BeingSlammed, BeingThrown, Impaled, Stunned, Shocked, BigTakeHit, Countered), as the game does in mode 7. A building falling on top still kills (it stays that way, the owner's decision). Grabbing works in multiplayer with both players in god mode. Known and accepted: with both grabbing on the same frame, one of them can stay frozen after being thrown away; turning god mode off and taking a hit brings it back to normal.
- **Win the fight:** `takeDamage(100000, force, jogador)` on each living AI, with the hit coming from the first player not dead (in the co-op campaign P1 may have left the stage, and their hit does not knock down) (`m_monsters[4 + i]`, `i < m_numAIs`); the game follows its own flow (death, victory, round count). With bosses that are not a regular `Monster`, the effect is unknown.
- **`WOTM_CHEATS=inv,stam|furia,esp,cloak,deus,vencer=N`** turns them on from the start; `vencer=N` repeats "win" every N seconds of game time (batch, advancing by itself). Example for batch: `WOTM_MATCH=3,1,1 WOTM_AIVSAI=1 WOTM_CHEATS=inv,esp,vencer=25`.

## Runtime: VU1 x native check (`WOTM_VU1CHECK`)
Compares, per object and in numbers, what the VU1 microcode would send to the GS with what the native layer draws. It does not produce an image. Code in `wotm_vu1check.inc` (runtime); hooks in `ps2_memory.cpp` (origin of each piece of the DMA chain), `ps2_vif1_interpreter.cpp` (origins up to each MSCAL/MSCNT), `ps2_vu1_core.cpp` (XGKICK output) and `main.cpp` (`hierFlushObjQ`).
- **How it works:** it runs in the usual native mode. VIF1 processes every chain that arrives (VU1 microcode and data kept up to date; without this only ~78% matched), but does not run VU1 nor feed the GS. Every `WOTM_VU1CHECK` seconds, on a fight frame (`g_frame` ≥ 30), `hierFlushObjQ` fires the real DMA from the entry of `hier(0, 0)` up to that of the next frame. Each XGKICK is taken apart into triangles (strip winding made equal to the native one) and assigned to the native object whose `polyPkt` contains one of the origins of the chain pieces since the previous MSCAL. At the start of each chain, the native layer collects the scene with the RAM of that instant and projects with the `worldToScreenMat` of view 0 (`d = p - olho`, `X = l0·d`, `Y = l1·d`, `W = l3·d`, GS pixels with center 2048). Each VU1 triangle matches the nearest native one of the same object (vertices within 1 px). Only triangles fully on screen (640x224) and not degenerate count.
- **Why collect per chain:** the chain references matrices and palettes in place (REF). Only the first packet goes out inside `hier`. At the end of pass 0, `hierCheckVifComplete` (0x2045A8, `bc0t`) says "busy" and the last packet, with the monsters, goes out through the DMA interrupt (`hierDmaHandler` → `hierFlushObjQ`), which the runtime delivers in the middle of the logic (`TheGame::Update`, `animationRunGlobal`). Collecting only at the entry of `hier`, the monsters matched at 20% to 99%, depending on the frame. Answering "free" in `hierCheckVifComplete` sent the packet twice. The camera is copied into the packet, and a pass 0 chain may go out already inside pass 1. That is why the native side is projected with the camera at the entry of each pass and the one that matches best counts.
- **Back faces:** the microcode discards back faces in sections with bit 15 of the selector (the native side too, `Vtx::cull`; rule and exceptions in lead 11 of `VU1CHECK.md`). Those that VU1 draws through the clipping path match against the ones discarded by the native side and count as `costas pelo recorte`. When VU1 drew no back face on an object, the leftover native ones count as `costas`, not as a difference.
- **Texture:** each matched pair compares the TEX0 in effect in the GS when VU1 drew (PACKED TEX0_1/TEX0_2 or A+D, between packets; context from `PRIM.CTXT`; `PRIM.TME` 0 = no texture) with that of the section's slot on the native side (`texKey`/`objectTex0`). Only the fields that pick the texels count (TBP0, TBW, PSM, TW, TH, CBP, CPSM, CSM, CSA).
- **Particles:** each system's packet sits inside its own `fx[i]` (`pkt` at +0), so the origin of the chain piece tells the system. VU1 sends each particle as two triangles (pedestrians, strips, type 7) or as a GS SPRITE (sprite, texSprite, debris, dust). The triangles become quads in pairs; the native side builds the same quads (`Particles::forEachQuad`, `Scene::spriteCorners` for debris), projected with the camera at the chain's instant or with that of one of the passes (the one that matches best counts). Each quad matches if all corners are within 1 px. Output: the line `[vu1check] g=… particulas: sistemas, quadrados vu/nativo, casados %, SPRITE do GS (fora de `fx[]`), vértices não comparados (só pontos)`, the line `particulas por tipo (casados/vu/nativo)` and up to 8 systems with the most difference (`fx`, preset, type, `n`, `sem pacote`).
- **Particle color:** in the matched quads, each VU1 corner (the vertex RGBAQ; for SPRITE, that of the 2nd vertex) against the nearest native corner, with the color the drawing uses (`Particles::forEachQuadColored`, which shares `quadColor` with `drawSystem`; debris: `Sprite::gsCol`). Line `particulas cor: casados com cor | cor difere (RGB > 4) | alfa difere (> 4) | por tipo (cor/alfa/casados)` and up to 6 systems with the 1st difference (RGBA of VU1 and of native).
- **Lines:** the XGKICK PRIM 1/2 (only `FX_LINE` uses them) against native (`pos` → `pos − vel`, the particle color and alpha 0 at the tail). It matches both ends within 1 px; `so a ponta casa` = the particle's end matches and the other does not. Line `linhas: XGKICK N segmentos (fora de fx[]) | vu, nativo, casados | cor/alfa difere`; dump `line,vu|nat`, `linecam`, `linemat`, `linep`.
- **Fans:** PRIM 5 becomes triangles (1st, second-to-last, last vertex) and enters the comparison like the others. In the corpus they all come from the microprogram's clipping and cross the screen edge (they count in `fora da tela`).
- **Texels (only in `--vu1cmp` with images):** each XGKICK TEX0 is read from the GS VRAM at draw time, the way the GS samples it (`decodeVram`: CT32/24/16, T8, T4, T8H/T4HL/T4HH; CSM1 palette by GS addressing), and compared, in matched triangles with the same texture, with what the native side decodes (`Scene::decodeTex`, raw alpha). RGB always, alpha only with TCC = 1. Line `texels: pares textura x objeto | iguais (<= 1), perto (<= 8), diferem, tamanho difere, VRAM com outra textura do mesmo TBP | uploads no quadro` and up to 6 worst (`texels tex <id>`). In the fight no texture is uploaded within the frame: they are already in the snapshot's VRAM.
- **Output:** per check, a line `[vu1check] g=… objetos vu/nativo/ambos | tris vu (repetidos: o mesmo triângulo redesenhado, como a sombra projetada) /nativo, casados % (sem os repetidos), faltam (do VU1, sem par nativo), sobram (do nativo, sem par) (costas) | textura difere, sem TEX0 | XGKICK (todos os triângulos do VU1), fora da tela | sem objeto, cadeias, tempo da coleta, …, VIF1 fora de passo` (invalid VIF1 codes since boot; nonzero = VIF1 read data as commands, see `VU1CHECK.md`). Then come up to 8 objects with the most geometry difference (`pkt`, `no`, `tex`, skinned, items), up to 8 with a different texture (`textura pkt`, with the most common TEX0 pair) and the origins of VU1 triangles with no native object. Collection costs 20 to 100 ms on one frame every N s. With `WOTM_VU1CHECK_DUMP=<prefixo>`, each check writes all the triangles to `<prefixo>_<g_frame>.csv` for analysis (last column: TEX0).
- **State and open leads:** in `VU1CHECK.md` (single source; do not duplicate here). References to "Corrigido" entries (here and in the code) are in the history: `git show 5eca44b:docs/passos/VU1CHECK.md`.
- **Snapshot and check without the game:** `WOTM_VU1CHECK_SNAP=<prefixo>` writes the session's sampled frames to a single file, `<prefixo>_<g_frame do primeiro>.vu1snap`: in the first one, the VU1/VIF1 state, the whole RAM and VRAM at the entry of `hier(0,0)` (~36 MB); in the following ones, the state and only the 4 KB pages that changed (~7 MB per frame in a fight). Within each frame, in the order they happened, each DMA chain (pages that changed, origins of the pieces and the bytes) and the entry of `hier(0,1)`. What VU1 sends to the GS is a function of only this (VIF1 reads the copy of the chain, never the RAM). `WOTM_VU1CHECK_SNAP_MAX=<MB>` (default 2048) stops writing at the ceiling. **Trigger, burst and shot cap:** `WOTM_VU1CHECK_WHEN=fx:<tipo>|preset:<fxId>|frame:<a>-<b>[,...]` only samples when the condition **becomes true** (edge: the event was born; a permanent emitter, like the volcano smoke, fires once, an explosion fires on each new explosion). `fx:` is the visual type, `preset:` is the system's `fxId` (names in `tools/fx.py`) and tells the volcano smoke apart from a building's; the `WOTM_VU1CHECK` period becomes the minimum rest between shots. `WOTM_VU1CHECK_BURST=<k>` samples `k` consecutive frames per shot and `WOTM_VU1CHECK_SHOTS=<n>` limits the session's shots. To see a rare event, do not wait for the clock: provoke the event (`WOTM_MATCH`, `PS2X_PAD`) and record the burst when it shows up. With the snapshot on, the runtime turns on `PS2X_GS_UPLOADS=1` by itself: texture and CLUT uploads reach the GS (without rasterizing), so the file's VRAM has the textures the reference image needs. It also intercepts `texmActivateTexture` (a miss in the stage texture cache): outside the sampled frame the `hier` chain does not go to DMA, and the upload of the swapped texture would ride on it; the hook sends the upload packet straight to the GS (the mipmaps of `texmSetMipMapTbl` are left out). Snapshots recorded without this hook have the old texture in those slots. `tools\vu1cmp.ps1 <arquivo ou pasta> [-Frame <g_frame>] [-Dump <prefixo>] [-Full] [-NoPng]` runs `ps2EntryRunner --vu1cmp <arquivo>...` (one run for all files: opening the runtime, with window and audio, costs more than the comparison; GS, VU1, the native presentation and the lens flares start from scratch for each file, and the output and images are the same as one process per file): it opens the runtime without the game, restores the state, replays the chains with the same native collection and prints the same `[vu1check]` output for each frame (that of the live check, except the collection time; seconds per session). A frame cut short by the death of the process is ignored with a warning; the previous ones count. The replay runs in a thread with a 512 MB stack: the main thread overflows. **Images** (default; `-NoPng` turns them off), next to the file, `<arquivo>_<g_frame>_{ref,nat,diff,trio}.png` at 640x448: `ref` is the runtime's software GS fed by the same packets (XGKICK, PATH2 and the frame's GIF channel), **an approximation of the PS2 GS, not the GS**: it is a guide for the eye, the criterion is still the table; `nat` is the native layer through the same function as the live game, with the RAM at the frame's entry and without the FPS counter; `diff` marks in red the pixels that differ by more than 24 in a channel over the darkened reference; `trio` is the three side by side. Expected differences: the `ScreenPolys` health marker, which the runtime's GS does not paint (PCSX2 does), the sky (GS gradient/dither) and the passes' camera. For the runtime's GS to draw the frame, the replay does a warm-up (runs the frame once through the GS only, returns VRAM and VU1 to the entry state, replays the GIF channel packets, which clear Z, and forces FRAME to this frame's buffer, because the frame's drawing environment was sent in the previous window). It serves as a regression corpus: a folder of sessions named for what they show, run in full after each change in `native/`. Delete the sessions once the correction is validated (rule from `CLAUDE.md`).
- **Out of scope:** vertex color, blending and alpha (the opaque explosion); VU1 lines (`line`) and fans are only counted.
- **Whole emulated path (without `PS2X_NO_VU1`):** the fight stopped on the first frame (`particleDraw` loop) and, with that loop released, crashed in `GS::consumeLocalToHostBytes` (VRAM read from `sceGsExecStoreImage`, called every frame from 0x2153FC). The check does not use this path. To locate a `[CRASH] exe+0x…`: relink with `/MAP` (`set _LINK_=/MAP:<arquivo>`, delete the exe and run `build_dev.bat`) and look for the largest symbol ≤ the address.

## Lessons on method
- **Object half disappears and the wireframe is whole: suspect the render state before the geometry.** The "holes" in the enemy monster were culling turned back on before the flush of the last batch (GL state applies at flush): flush (`rlEnd(); rlDrawRenderBatchActive();`) before changing state. A long hunt in palette, weights and pose found nothing because mesh, palette and matrix were right.
- raylib: `rlBegin` with a different mode resets the texture (call it before `rlSetTexture`) and flush the batch on each texture change.
- `WOTM_NOSKIN` is not a reference pose (positions are local to the bone); `WOTM_ONLYTEX` alone removes body parts and creates false holed silhouettes.
- `getenv` inside the `drawList` vertex loop drops the menu to ~1.6 FPS.
- A retail dump from PCSX2 has the geometry, but the texture pixels have already been reused; since `texInfo` is identical between retail and runtime, copying the pixel packets from the runtime dump gives a textured **hybrid dump** in the retail pose.

## Movies (FMV)
- **Cut:** the game's decoder (SCE's "ezmpeg" sample, IPU via DMA) depends on the IPU, which the runtime does not emulate. `native/wotm_fmv.hpp` replaces `playMpegMovieWithDB` (0x20F4B0) and `updateMpegMovieDecoding` (0x20F540) for the full-screen ones (at the end: `movieRequested` 0, `movieIsPlaying` 0, `movieIsCompletelyFinished` 1) and `CMovie::Play/Update/End` (0x210090/0x210408/0x210360) for the movie on the menu's big screen (`mov/sheldemo.pss`, looping). `Update` redoes `moviesSetScreenObject`: the big screen object gets texId 999 (TEX0 CT32 at 0x3BA0, 256x128), which `Scene` swaps for the player's texture.
- **Format:** video 0xE0 (MPEG-2 via `libavcodec`, BT.601), audio in private 0xBD (`SShd`/`SSbd`, 16-bit 48 kHz stereo PCM in blocks of 512 bytes per channel, which FFmpeg does not recognize). `docs/FORMATOS.md` ("`.PSS` movies"), `tools/pss.py`.
- **Runtime:** `PS2X_FMV=1` (`wotmFmvInstall`; takes precedence over `PS2X_SKIP_MOVIES`/`SKIP_CMOVIE`; in `wotm.exe` it turns on by itself if none of the three is set, FRONTEIRA step 9); `.PSS` from the disc folder or from the ISO (`PS2X_CD_IMAGE`; `WOTM_DISC`/`WOTM_ISO` force it), `WOTM_FMV_MUTE=1`. Skip: Space/Enter/cross/start (`skip_` -> `continuar = 0`), from the raylib keyboard/gamepad or from the pad the game reads (`inputPadData`, new press of X/Start: works for the `PS2X_PAD` script), without the 600-frame wait that `uiMain` imposes on `intro_m`; the "Sony presents" and "trademark" screens are the first ~10 s of `intro_m.pss`.
- **Pitfall:** `Movie::close` must clear the L/R pair being assembled (`blk_`), otherwise the next movie comes out with hiss.
- **Missing:** the audio follows the wall clock, not the game's; the blocking `playMpegMovie` (0x20F440, no caller) is left out.

## Camera and snapshot
- **Camera:** `worldToScreenMat` embeds the axes (row 0 = 384·right + 2048·forward, row 1 = −180.48·up + 2048·forward, row 3 = forward; in the menu the horizontal focal length is 496). The vertical FOV comes from the matrix itself (63.6° in gameplay); do not mix it with the `_cs` read at another instant. **The eye comes from `worldCtx[view].eo`** (+0x20, = −`cs->trans`), which `viewUpdate` writes together with the matrix, and forward and up come from the matrix itself. `_cs` is only a fallback in the menu. In the fight intro (the camera rising along the building), the game puts another camera in the same `_cs` (0x800d30) for an instant in the middle of the frame. The matrix keeps the right one. The native read caught that instant, sometimes halfway (x and y from one camera, z from the other), and the screen cut for one frame to another corner of the map: 14 times in 50 s with the raw `_cs`, none with `eo`. The `[cam]` line of `WOTM_CAMLOG` has `cs=` (pointers of views 0 and 1), `wm3=` (forward of the matrix), `csp=`/`csu=` (position and up of `_cs`).
- **Presentation rate (`wotm_live.inc`, `initPresentRate`):** the window presents at the monitor rate (`GetMonitorRefreshRate`; `WOTM_HZ=<n>` pins it) with vsync (`WOTM_VSYNC=0` turns it off), in place of the fixed `SetTargetFPS(60)` of `ps2_runtime.cpp`. The game logic stays at 60, so the scene is only **redrawn** when a new snapshot arrives (or when the `Shell::FadeScreen` fade changes, with the free camera paused, with the window resized, or at ~60/s if no frame has arrived for 40 ms: pause and loops without capture); in the other presentations the last image is just presented again. The cost stays that of 60 and texId 0 (previous frame) is still the previous drawing. On a 180 Hz monitor that is ~176 presentations and ~60 redraws per second (`docs/screenshots/2026-10-18/2026-10-18_apresentacao_180hz_luta.png`). `PS2X_STATS` shows `redesenhos=` in the `[native]` line and, every 300 presentations, the average time of each redraw with 1 and 2 views (wall and CPU of the window thread; `[native] redesenho:`). The runtime's per-presentation counters (`PS2X_SHOT_FRAMES`, `PS2X_COVERAGE` every 300, `PS2X_DUMP_RAM`) count presentations, which are 3 per game frame on a 180 Hz monitor. **Frame interpolation** (option INTERPOLATE FRAMES, `WOTM_INTERP`, on by default; table below): it applies with presentation above 60 Hz, or up to 60 with the game at 30 (half or more of the last 64 frames with a 2-field gap turns it on, up to 1/8 turns it off; with the game at 60 it would only add a frame of latency). If the redraw does not fit in the presentation period (moving average of the redraw block time, `g_drawMs`, each sample capped at two periods, above 85% of the period), blending is suspended and resumes below 60%, with an `[interp]` line in the log: with vsync dropping to half the screen would be worse than without it. With it, every presentation redraws the blend of the last two snapshots (`Scene::showBlend`): items matched by `(cs, nó, ocorrência)`, matrix decomposed into per-row scale, rotation (slerp) and translation; bone palette bone by bone; camera with linear position and FOV and axes by nlerp; a camera cut (400 units, `dot(frente) < 0,7`, FOV changing more than 5°, another view) shows the newest frame; HUD, icons and the high-priority list go to the blended camera by their position relative to the newest frame's camera. The displayed instant follows a clock in fields (`Snapshot::fields`, the counter at the start of the frame, and `Snapshot::hostT`, the capture time; the offset between the two is filtered at 5% per frame), one game frame behind the newest and 3 ms of margin; when the new frame arrives early, the blend is that of the previous pair (`State::prev2`). The capture culls by sphere with a radius 1.2 times larger (`Scene::cullMargin`), so the delayed view does not lose objects at the edge. Cost: one redraw per presentation (at 180 Hz, ~2.5 ms with 1 view and ~4.6 with 2) and +1 frame of latency. **Particles and debris** step back from the newest frame by their own velocity, `(1 − α)` of a `particleMove` step (`Particles::stepBack`: `pos_B − pos_A = f·(vel_B + vento − (0, 0, gravidade·f))` in `f` fields; wind with the `Gusts` gusts; no gravity for dust, wake and kite; z pinned for wake and kite on the water): the first `n − newParticles` of each system, because the ones at the end were born in the step and stay where they are. `Particles::blendRam` builds, in a shadow copy of the `Scene` (`fxMix_`), the B strips with the stepped-back positions, and writes into it the `worldToScreenMat` and the eye (`worldCtx.eo`) of the blended camera (`M' = M_B·C_Bᵀ·C_I` in columns 0–2, C = camera axes), which the strite, the line and the fog read. Debris (`Sprite`) saves the step at collection (`Sprite::step`, `Sprite::grav`). Size (`pos.w`), age and color stay those of B. Arcs, sprine, chain and trail (points placed by the game) and the emitter's motion (fire attached to the monster) do not step back. **2D tied to 3D:** the lens flare, which the game projected with B's camera, is unprojected with it (by depth W; the one at infinity only by direction) and projected with the blended one (`Scene::blendFlares`; W and the GS Z redone, whatever leaves the screen or falls behind the camera disappears). The focal length comes from the view's `worldToScreenMat` in the shadow copy, scaled by the blended FOV. Bars over the enemy and the health icon (`Scene::blendAnchors`, `anchorShift`) follow the annotated world point (`HudAnchor`), matched with the nearest icon from A (same view, up to 100 units): if the icon is at the same distance from the point's projection in A and in B, the blended point goes through the blended camera; if not (the game clamped it to the screen edge), it blends the screen position. In split screen the presentation loop does this view by view on a copy of the bars, of the game icon (whole-window polygons) and of the flares. The fades' alpha blends with A's when the rectangle (place, color, texture) is the same. Text and `Shell::FadeScreen` (loop without capture) stay those of the newest frame. **Tied to the camera outside the HUD lists** (menu panels, view-aligned objects): the matched object whose pose relative to the camera is the same in A and in B goes with the blended camera, like the HUD, instead of blending the matrix in the world. **Cut:** a view that appears or disappears (split screen turning on, unified grapple view) has no pair and comes out as B. **texId 0** (video environment map, CLOAK) reads the previous presentation, closer in time than the game's previous frame. The launcher detects the resolution and rate of the main monitor (current mode, in real pixels) and, with no saved configuration, suggests the largest resolution that fits in it.
- **Widescreen (Hor+):** the native frame is 720 tall (`WOTM_RES` changes it) and as wide as the aspect ratio (`wotm_live::viewAspect`): the vertical FOV is the game's and raylib widens the horizontal one by the render target's aspect ratio. The window opens at 1280x720 and the aspect ratio follows the window (from 4:3 to 32:9); `WOTM_ASPECT=L:A` pins it (`4:3` = original screen). The GS screen (640x224) becomes the central 4:3 band of the frame (`gsScreenRect`, `wotm_fx.hpp`): game text, lens flare (Z test and sprites) and the UV of the previous frame (texId 0) go to it; the `hier` HUD already stays in it because it is projected in front of the camera. Native collection does not clip by the game's frustum, so the sides appear whole; only particles go through `viewInFOV`, which in widescreen swaps the side planes (`planes[0][1..2]` from `viewSetFov`) for those of the wide screen (`Particles::inViewFov(..., wide)`). The game does not change (the retail AI and `viewInFOV` stay at 4:3). Limits: the lens flares come from the game's list, projected and clipped at 4:3 (a source only on the sides does not shine); the replay (`--vu1cmp`) forces 4:3 (`g_force43`), because the GS reference is 4:3.

- **`native/wotm_fx.hpp`** (`Scene::fx`): cut before `particleDraw` (0x21B378). Gathers the active systems with the `particleDraw` tests (including `viewInFOV`) and draws last (depth test, no depth write, farthest to nearest). ## Menu text and buttons
- **Text:** comes from the font hooks (`wotm::FontText` in `wotm_native.hpp`; hooks in `wotm_overrides.cpp`): `fontInitPacket` (TEX0 of the boot atlas), `fontSetTexId` (atlas from the `.RTX`), `fontSetColorGifTag` (color; with an empty packet it rewrites the header color, which takes effect at the start of the next frame), `fontBuildPrim` (one glyph, with the same computation as the original from `fonts[2]` and the current view's `viewDef`) and `fontDmaFontData` (closes the frame). The glyphs are the same as in the packet. The replay (`--vu1cmp`) still reads `fontPacket` from the snapshot (`Scene::updateText`). The `ScreenPolys` HUD comes the same way, through the `polyBuildPrim` hook (`wotm::screenPolyFromCall`: `resolveFX` and the sprite rebuilt from the arguments, equal to the packet); the replay reads `s_polyBuffer` (`readScreenPolys`). Packet format: A+D tag (`TEX0_1` = PSMT8H 512x512 atlas), `[PRIM,RGBAQ]` + color, `[UV,XYZ3,UV,XYZ2]` with `NLOOP` sprites (12.4). 640x224 screen: `x - 1728`, `y - 1936` (split screen not handled yet). Color: the GS does texture·color/0x80 and saturates, so the shader doubles the RGB.
- **Button icons:** `CS` from the `McButtons` pool (ids `0x1F51..0x1F54`, `0x240E..0x2411`) placed by `AlignCsWithView` ~80 units in front of the camera; they ended up below the drive-in floor. They go to `Scene::overlay`, drawn last without depth. **Fade:** `screenSetButtonAlpha` copies `targetAlpha` to `+0x4C` of the child object; `drawList(..., fadeByNode=true)` multiplies the alpha by that float.
- **Fades:** the game darkens the screen with an untextured GS SPRITE (ABE, `ALPHA_1` 0x44, color of the whole view, alpha 0x80 = covers) built on the spot: `rtFadeScreen` (fight entry, alpha 0x80 − 2·g_frame), `TheGame::updateFadeOut`/`updateFadeOutAndIn` (end of round, cinematics, camera change) put the packet in the `gsPkt` queue; `uiFadeScreen` (menu entry) builds it on the stack and sends it directly; `Shell::FadeScreen` (menu → stage, end of loading) is a loop of its own that waits for vsyncs. The native layer rebuilds the rectangle from the arguments, without reading the packet (hooks in `wotm_overrides.cpp`, computation in `wotm_live.inc` with `wotm::viewFadeRect`): `rtFadeScreen(view, amount)` and `uiFadeScreen(amount)` give alpha 0x80 − amount over the whole view; `TheGame` is read on return from `updateFadeOut`/`updateFadeOutAndIn` (level at `+0x120450`, one view per player, only view 0 with a movie or a single view); the list goes into the snapshot (`Snapshot::screenRects`). `Shell::FadeScreen` does not go through the capture: the entry stores view, color, start, end and step, and each `sceGsSyncV` of the loop advances the alpha (`wotmShellFadeStep`/`wotmShellFadeStepDone`); the presentation uses that alpha until the next capture. With `b = false` it does not redraw the scene and repaints the fade over the same buffer every field, so the darkening accumulates (Π(1 − a/128) over that buffer's alphas) and the native layer draws the equivalent alpha. `Scene::drawScreenRects` draws after the text; a rectangle as wide as the screen covers the whole window (widescreen), a smaller one stays in the 4:3 band. Picture: `docs/screenshots/2026-10-16/2026-10-16_fades_menu_e_entrada_da_fase.png`; the VU1 x native check does not see the fades (replay without the hooks). **Stage load:** after `Shell::LoadLevelFiles` puts the new level in RAM, `loadResources` swaps the textures for the level's, and the `LOAD` card, if redrawn, would come out with some random texture of the level (a "green sphere" on the loading screen, the power-up glow in CENTRAL, and a green, red or white light in the middle of the screen when the match starts, depending on the stage). On the PS2 the screen stays frozen on the last frame of the card: the load bar is drawn directly into the frame, without `hier`, and the `FadeScreen(0, false, ...)` after `FinishLoadBar` only darkens that image. So, from the entry of `LoadLevelFiles` to the entry of `rtMain` (hooks in `wotm_overrides.cpp`, `wotmLoadFreeze`), the capture publishes nothing and the presentation repeats the last drawn frame, with the `Shell::FadeScreen` fade on top. The load bar still does not show (it does not go through native drawing). The card fade-in (the `FadeScreen` with the `DisplayLoadBackground` redraw, which does `hier(0, 0)` and `sceGsSyncV` per step, without `timerWaitForMinUpdateRate`) does not go through the normal capture: the `sceGsSyncV` hook recognizes the loop's two return addresses and publishes the scene of the step without turning the fade off (`wotmCaptureFadeStep`).
- **Menu black bars:** in the menu the cinema bars are not the HUD `Letterboxing` (that one belongs to the story mode cinematics and intros) but `letterboxDmaData(alpha)`, which `userintMain` calls between `hier(0,0)` and `hier(0,1)`: two black 24-line SPRITEs at the top and bottom of the view, alpha `alpha·128`, without A+D (it uses the `ALPHA_1` 0x44 in effect). Rebuilt at the entry from the alpha in `$f12` (`wotmLetterbox`) and drawn with the `underText` rectangles: after the scene, before the high-priority list and the text. They cover the width of the view, so in widescreen they span the window from side to side.
- Old menu issues, not rechecked after the fixes: logo and "player 1" without color, dark and grainy cars (maybe reflection maps), wooden lattice with dotted alpha (texId 166; probably original).

## Projected shadows
- **Retail (`common/ps`):** up to 10 blockers in `psBlkLst` (0x51C600, 0x30 B: `cs` +0x10, second `cs` +0x18, radius +0x20, factor +0x24 (9), range² +0x28 (1200²), in use u16 +0x2E; `psBlockerAdd`), drawn from the light direction (`psLitDirWs`, 0x54CC90; view 4) into a small texture, filtered and reprojected onto nearby objects. Active if `psSetShadowOnOff` (0x6F8D7C), `cs->drawMe` and the view bit in `cs+0xE`. Intensity `psShadowIntens` (0x6F8820) = 80.
- **Native:** `Scene::collectShadows`/`drawShadows`: only objects without `dontCastShadow` (bit 29 of the OBJECT bits at +0xC; `psBldBlkRObjs` skips them: on Kineticlops only the eye casts) go into the silhouette, rasterized on the CPU (128x128, orthographic, half-side `radius * 1.1`, two 3x3 box passes) and reprojected onto the objects whose sphere crosses the shadow cylinder. Differences: orthographic (retail: perspective with `psZoomT`), approximate filter, silhouette LOD. **Validated only with a synthetic scene.** The silhouette uses the `hierShadow` LOD (fixed blocker distance, `psBlkLst + 0x28`) and is not clipped by the view; it is reused across redraws (same inputs) and across the split screen views (tolerance of 1.5 units), and uses the snapshot palette (`forEachTriPos`).

## 64 MB RAM and loading above 32 MB
- **The runtime has 64 MB and the game sees 32.** In the runtime patch (`ps2_memory.h`): `PS2_RAM_SIZE` 64 MB and `PS2_GUEST_RAM_SIZE` 32 MB. The
  main thread stack (`SetupThread` with stack -1), `GetMemorySize`, the runtime heap and the async callback stack
  follow the second one (`System.cpp`, `ps2_runtime.cpp/.h`), so everything the game allocates sits where it would on the PS2; the upper 32 MB only
  receive what the hooks send there. Addressing is by mask (`PS2_RAM_MASK`). Applies to both executables.
- **Monster load** (`wotm_overrides.cpp`, `loadMonstersDBHigh`): at the entry of `Shell::LoadMonstersDB` the next load
  address (`fileStatus.ngpAddr[ngpLoaded]`, right after the stage NGP) becomes 0x2000000. The monster NGPs and, behind them, the RTX and TEX
  of the stage and of the monsters go up; only the stage NGP stays below. Relocation (`dbsRelocateViaPtrListFile`) adds "address -
  0xA00000" in 32 bits and works at any address. `WOTM_HIGHRAM=0` goes back to the PS2 contiguous load (with 8 monsters, Metro goes past
  32 MB and freezes). The `[wotm] carga da fase` line says how much is left to the end of RAM, and `N de 1000 texIds` warns near the ceiling of
  `texInfo`. The `VRAM residente até ..., cache de texturas com N KB` line gives the end of the `.RTX` files (`startVramAddr`) and the space of the cache
  of the `.TEX` files up to `lastVramTexAddr`. `wotm.exe` draws from RAM and does not depend on the cache. In Canyon with 4 players and 4 AIs: 238
  texIds, 2134 KB of cache and 20.8 MB free in RAM; with 1 player: 196 texIds and 2164 KB. In Capitol with 4 players (jelly and
  Mecha): 293 texIds, 2121 KB and 22.6 MB.
- 32 MB snapshots still open: the replay accepts a RAM smaller than the build's and zeroes the rest.

## Save as JSON (`wotm_save.inc`, `wotm_json.hpp`)
Format of the memory card binaries: `docs/FORMATOS.md`, "Memory card save". `WOTM_SAVEJSON=0` turns it off (only `mc0/`/`mc1/`).
- **Hooks:** at the entry of `MonsterMc::stdInit` and `MonsterMc::stdExit`, which open and close every sequence of memory card pages.
  In `stdInit` the binaries of both cards are rebuilt from `save.json`; in `stdExit`, if the game wrote any binary (date or
  size changed), the JSON is updated from it. The game sees the same 0x380/0x280 bytes; the stack garbage (0xF4 onward, except the
  mark) becomes zero.
- **A single JSON**, next to the memory card folder (`discroot/save.json`): `options`, `battleTokens`, `unlocks` (monsters and costumes, stages),
  `records.enduranceBest` (`easy`/`medium`/`hard`) and `unknown` (the unnamed fields), once for both cards; `saves` with up to 99
  slots (`null` = empty; the array ends at the last occupied one). The `savegame.dat` of card 1 carries slots 0 to 9 and that of card 2 slots 10 to 19; the
  others exist only in the JSON. Keys by name (`"congar": {"skins": [...]}`, `"levels": {"ufo": true}`, stage and monster of the saves by
  name), never by index: a mod that adds a monster or skin only adds keys. Keys the code does not know stay in the file
  when it is rewritten. `unlocks.mechaSweetTooth` takes precedence over `agamo.skins[3]` (created from the card state when missing). The
  old `unknown.game1204B0` is still read and dropped on rewrite.
- **Adventure costume by name:** the slot stores `"costume": "ultra-v/roxo"`; a single `resolveCostume` serves `jsonToAdventure`, the
  save list and the 3D monster. Missing skin: costume 0, log and "skin missing" in the list; saving the same adventure puts the name back in the JSON
  (forgotten when a monster select screen opens). `adventureToJson` leaves alone a slot that says the same as the binary.
- **Co-op adventure:** saved with 2 to 4 players, the slot gets `"coop": [{"monster", "variant", "lives", "costume"}, ...]` with
  players 2..N (`m_monsterSel[i]`, `m_lives[i]`, `m_costume[1]` and costumes 3 and 4 from `wotm_split4.inc`); the top fields are
  player 1, and the binary stores only that player (a PCSX2 sees a 1-player adventure). The save list shows "N players" on the lives
  line. Loading a co-op slot (`wotmCoopLoadArm`, `wotm_padsel.inc`): the load from `updateStoryModeLoad` (`changeScreen(9, 0x63)`)
  becomes `changeScreen(9, 5, -1, 9)`, the controller selection (screen 5, camera back to the big screen) with "SAVED ADVENTURE FOR N PLAYERS", and
  Start only goes on with N players (bots count). On confirmation, players 2..N of the slot, the stage AIs (`adventureAis`) and
  `changeScreen(5, 0x63)` come in; triangle from whoever is out goes back to the main menu.
- **Migration:** without a JSON, the first `stdInit` creates it from the cards; with a JSON lacking the slots of a card that has adventures, they
  are imported. A JSON that does not open is reported in the log, the cards stay as they are, and before the game rewrites it the user's file
  goes to `save.json.bad`. Writing goes through a temporary file and a swap. The `[wotm] save: no jogo, N tokens, dificuldade D` at the end of
  each sequence says what the game has in RAM.
- **Autosave** (always on): the six `MonsterMc::update*` that are not adventure ones (`BootLoad`,
  `SettingsLoad`, `SettingsSave`, `UnlockSave`, `EndOfStorySave`, `EndureSave`) become a direct copy (the same as `getSettingsData`/
  `setSettingsData`) between RAM and `save.json`, which sets `+0`, `+4` and `McPageMgr+0x130` (sequence finished: the options screen only
  comes back with it) in the same call. The callers only repeat `update*` until `MonsterMc+4`. The swap keeps the unlock screen purchase
  inside the save (like `McSaveSettings::update`), and the boot still normalizes mono and applies volume and vibration in the
  caller. Tokens the game adds outside the sequences (end of a story stage) are caught by a watcher on `sceGsSyncV`: tokens or
  unlocks different from the last save go to the JSON (only those: the options menu may hold values not yet accepted). The end of
  endurance stores the larger of the record and the monsters defeated by player 1, in RAM and in the JSON (`[wotm] save: recorde do
  endurance (medium): 0 -> 5`).
- **Save list** (adventure, in place of the boxes, the tapes and the card choice): loading goes up to the boxes in the menu map
  (`McPrepBoxScreen`), and the update of `McLoadGameBoxes` becomes a modal with the `McBackground` frame and the `McTextBox` text (fonts
  of `McPage` scaled down). On the right, the list from `save.json` (10 visible, up/down wrapping at the ends, left/right by 10 at
  a time); on the left, the chosen save: monster logo, "on <stage>", the wide picture of the stage with the 3D monster on top, "Score N", lives and
  "N of 11 levels" (the menu font has no `%`, `:` or `/`; the save's stage is the next one to play). X loads through
  `MonsterMc::setSaveData`; triangle/circle goes back. Saving: the update of `McChooseSlot` (after the "save?") becomes the same modal;
  an empty slot saves directly, an occupied one asks for a second X. The first 100 ms do not read the pad (the X from the "save?" would arrive here). In the stage the
  frame is lower (the size comes from the `McBackground` animation, and `setDestDims` does not go past 1): the text heights are
  compressed, the frame goes straight to its final size (`timerGetFieldsLastFrame` does not advance there) and `+0x274` of `McChooseSlot`
  (`stateIsOk`) is set as in the original. The controls legend only shows when loading (in the stage the black band would cover the fight).
  No memory card message shows in the game.
- **List images** (`native/wotm_savepics.hpp`): they come from `SHELL/SHELL.TEX` + `SHELL.RTX` on the disc (folder or ISO; after the fight the
  menu is not in memory): 256x128 logos at texIds 121..129 and 52 (Raptros); 512x256 pictures in two 256x256 T8 pieces (the square
  picture in the previous piece is not used). The palettes are 16x16 entries of the `.RTX` allocated in texture order (4 per T8, 1 per
  T4; the `.NGP` does not bind these, the menu swaps them by switch). The rows are bottom to top. The modal posts the list every frame and the
  window draws between the frame (high-priority list) and the text, with a 0.2 s entry. Without a logo (Spider, Ogre...) the name comes out as
  text. The 3D monster is the one from `wotm_model.hpp` (`MODELOS_3D.md`). A snapshot with fewer than 20 items counts as "no stage" (black
  screen), except with a dialog in the high-priority list (the "save?" after the final Tsunopolis scene). The count adds what
  `collect` culled by the view (`Snapshot::culled`): the visible ones alone gave fewer than 20 with the camera facing space in UFO or
  pressed against a wall, and the whole fight went black.
- **Save icon** (`native/wotm_saveicon.hpp`; `WOTM_SAVEICON_TEST=1` shows it every 3 s): the `MEMCRD/ICON.ICO` from the disc (format
  in `FORMATOS.md`). Each write of `save.json` increments `g_wotmSaveCount`, and `wotmDrawScene` draws the spinning tape in the bottom right
  corner for 1 s (0.15 s fade). Reads from the disc folder, from the ISO (`native/wotm_disc.hpp`) or from the copy the game wrote to the memory card. The
  `icon.sys` lights are not used.
- **Caution:** editing `save.json` with the game open can clobber a write (an editor open from before rewrites the old
  version). Edit with the game closed.

## Enemy bars (`WOTM_ENEMYBARS`)
- A block over the head of each enemy, in place of the health icon (hook in `Hud::drawHealthIcon`/`ScreenPolys::addPoly`):
  portrait at full height on the left; on the right, health (`m_health`/`m_maxHealth`) on top and, below, the special button and the energy
  (`StaminaMeter`, +0x460; thinner and shorter). Each piece has its own black outline, the gray band between them is shared and there is a
  black outline around the outside. Drawn through `ScreenRect::tex0` (`wotmBarTex`), respecting the split screen clipping. They go under the player's HUD: `Scene::draw` draws them in 2D right before the `hud` list (`Scene::barPass`, one pass per view in split screen, each view in its own texture), and `drawScreenRects` skips them (`barsUnderHud`); without `barPass` (replay, corpus) they come out at the end of the frame, on top of everything.
- **Portrait:** last entry of the monster's `.RTX` (T8H 128x64; left half normal, right half rage). The hook finds the monster's file
  through the `epNode` of `m_cs` (+0xC) and the ranges of `fileStatus.ngpAddr`, and searches the NGP for the TEX0 of that portrait
  (`tbp0 == maxResAddr[i-1]`); cached per stage load. Rage = `m_boostFull` (+0xF4), the same key as the `hierSetSwitch` of
  `Hud::update`. The texture is upside down in VRAM (the game draws with V = 0x80 - v): the rectangle goes from V 64 to 0.
- **Special lit** = `m_specialWeapon` (+0xF3) outside mode 9, like `isSpecialAvailable`, in the red of the player's HUD icon.

## 3 and 4 player split screen (`wotm_split4.inc`)
Always installed: it acts when the game has 3 or 4 players (through the multiplayer menu or `WOTM_PLAYERS=3`/`4` with `WOTM_MATCH`). The engine
already has `viewInfo`, `worldCtx`, `viewDb`, look-at points and the particle `viewPrevMat` with 5 views, 4 cameras, 4 HUDs,
`m_monsters[0..3]` for players and 4 `TokenManager`; `inputInit` opens 2 ports × 4 slots (controller = port + 2 × slot);
`SoundManager::m_events` is `[4][4]` by `m_index`. The cinematics' `viewToggleSplitScreen` does nothing with 3 or more views. The hooks:
- **Views:** on exit from `gameReestablishViews` (modes 3, 6, 7) views 0 to 3 become 320 × 112 quadrants (column `v & 1`, row
  `v >> 1`). With 3 players view 2 is the whole bottom row, 640 × 112, with a screen distance of 2/3 of the full screen
  (`kStripFov`: the quadrants' one would give ~118 degrees horizontally; the full screen one would cut the monster vertically); native drawing
  gives it a texture as wide as the window (`stripView` in `Scene`, for the bars over the enemies and its native HUD). The 4 `ViewDef` live at the end of the upper RAM (retail only has
  8, none in a quadrant), with the full screen's screen distance halved (same FOV as the 640 × 224); `viewSetFov` rebuilds planes and
  matrices.
  `viewInfo[v].viewport` stays 1/2 (the cameras use the split screen POV table). `m_numCameras` = players.
  `viewGrappleConfig` puts view 0 back on the half's `viewDef`: the hook reapplies the quadrant.
- **No unified view:** camera 2 (retail's unified one) is player 3's. `SetOkToUnify` zeroes `m_camUnify` every frame
  (`InitCCCamera*` returns without unifying). The victory pose unifies (full screen on camera 2); when the screen splits again, cameras
  2 and 3 go back to players 3 and 4. `ResetLevel` does not change camera 2's POV. Retail's `LeaveUnifiedView` only treats 2 monsters as
  split screen; with the quadrants it takes the 2-player path.
- **AI cameras:** retail's `SetAIMonster` puts every AI on camera 3 (`gameInitCamera(3, ai)`); here the AI only gets
  `m_cameraView` 3. `StateThrowBack::handlePreemption` (end of being thrown) puts the owner's `m_cameraView` camera in POV 0 without
  checking whether it is human; with an AI owner camera 3 does not change (`enterSubState` and `StateButtSlam` already check `m_playerNum`).
- **POV 3 of cameras 2 and 3:** POV 3 is the camera parked at `+0xD20` (`DetachCamera`, `TogglePOV`), which cameras 2/3 never have
  in retail. On entering POV 3 it parks where it is; camera 2 leaves the initial POV 3 (rest position of the unified one) for 0.
- **Load:** from `LoadLevelFiles` to the entry of `InitPlayers` players 3 and 4 go through the AI path (`m_monsterSel[4..]`,
  `m_costume[2..]`, same disc file) and then go back to being players; `SetPlayerMonster` gets their costume instead of
  `m_costume[1]`. In retail, `LoadMonstersDB` builds the path of players 3/4 with player 2's monster. Players 3 and 4 take
  their controller configuration from `m_vibration[0..1]` (`Monster::playerInit` reads `m_ctlrCfg[m_index]`, which only has 2).
- **HUD:** retail's `Hud::initAfter` and `Hud::update` return right away with index ≥ 2. HUD 2/3 is a copy of the HUD of the same column
  (`i & 1`), where its messages live, but its update does not run: the copy shares with the HUD above the bar's `_cs` and the
  animation instances. The HUD of views 2 and 3 comes from the native layer (`wotmPlayerHud`, `wotm_overrides.cpp`), in the game's HUD
  drawing: portrait (the rage face with `m_boostFull`), health with recent damage in red, special button and the stamina standing up,
  bottom to top (what goes past the maximum in pink; blinks when the rage is full), with the boxes of the full screen P1 HUD
  (`wotm_training::hud`) at half scale in the top corner of the view, mirrored in the right column. In the bottom band of 3 players
  the x of the HUD rectangles (`ScreenRect::hud`) comes out at 1/4 of the window + (x − 320) × 2/3 of the quadrant scale; the HUD goes to
  80 + 3/4 x, in the same place of the window as view 0's. The enemy bars in the band come out at the quadrant scale, centered
  in the window (`barSpan`), and go from edge to edge. The native HUD rectangles come out after the enemy bars, on top of them. Hidden with `gHudEnable` zeroed, letterbox, unified view and full screen cinematic. In place of the update: the bar of the
  column turned off in the view's `hier` (the update of the HUD above turns it on again before its own), the `updateMessage` of HUD 2/3 with the
  column index (text side) and the "WINS n" of modes 2 to 6 with the same font calls as `Hud::update`. The low
  energy sound of players 3 and 4 does not play. With `m_numMonsters` ≠ 2 the bar of HUDs 0 and 1 stays in the full screen position, which is the
  quadrant layout. The HUD text is placed as in a 224-line view from the top of the quadrant: in the native layer, what
  falls in the lower half (the "WINS") moves up 112 (only when more than one view sends text; the pause dialog stays as it is). The
  enemy bars turn on by themselves with 3 or 4 players.
- **End of round (mode 3):** `EvaluateMultiPlayerBattleStatusNoAI` only handles 1 or 0 alive and `...AI` respawns slots 0/1 as
  players and the rest as AI. With the quadrants both change: win target as in `...AI`, otherwise each dead one in `m_monsters`
  respawns through `playerInit` (players) or `aiInit` (AIs). Dialog 5 is **modal** (runs frames and yields to the scheduler): it is called
  as a tail call, with the `ra` of the caller of `Evaluate` (through `callGuest`, with `ra` 0, "play again" would return to pc 0 and kill the thread;
  the runtime warns `[resume] thread N terminou em pc 0`).
- **Cinematic** (presentation before the fight): at the start of each frame, cinematic on puts the screen in a single view (`viewNumViews` 1, view 0
  with `viewDef[0]`, 640 × 224) and cinematic off goes back to the quadrants, like retail's 2 players. On the way back all views are
  rebuilt (`endCinema` calls the toggle, which with 1 view recreates views 0 and 1 as halves).
- **Start:** in `gameGetStartPoint` (modes 2 to 6) the first human spawn uses `StartPoints` list 1 and the AI one list
  2, in rotation; respawns, list 3. List 1 only has the points of retail's 2 players; the player beyond them spawns as an AI
  (`m_playerNum` 2 during the call), in list 2. On "play again" everyone respawns through list 3 (4 points); whoever lands less than 120 from
  another goes to list 2 (two monsters on the same point put NaN in the position through the push).
- **Motion blur:** `MotionBlurAA::init` builds a 0x100-byte packet per view in a bss block where only 2 fit; init keeps 2
  views and `drawOverlay` of views 2 and 3 sends nothing (the native layer does not draw the blur).
- **Controllers:** the runtime stub only has slot 0; the `scePad*` with slot 1 are answered like slot 0 of the port, and `scePadRead` of
  slot 1 reads the devices of player port + 3 (`wotm_pad.inc`): third and fourth raylib controllers (`PS2_PAD_MAX_GAMEPADS` = 4).
  The `PS2X_PAD` script accepts `@3` and `@4` (slot 1 of the ports).
- **Native:** `Snapshot::views[3]`; capture of views 2 and 3 on exit from `hier(v, 0)` (fallback: entry of `hier(v, 1)`); quadrant
  textures composited with the black bars in a cross; vertical FOV by the view height (only in the `ViewDef` above 32 MB); text, bars
  over the enemies, flares (`lensFlarePacket[v & 1]`, one copy per view, occlusion by the depth of the previous redraw) and the previous
  particle matrix for 4 views. Shadows are rasterized once per redraw, with the shadow LOD like `hierShadow`.

## Elimination and minigames with 3 and 4 (`wotm_modes4.inc`)
With 3 or 4 players screen 5 shows the retail list (free for all, elimination, minigames) and only the monster selections are ours
(the big screen one; in the minigames the choice from screen 14 comes to screen 6 instead of the arcade, with camera animation 8 reversed). Direct
match: `WOTM_MODE`. The rules, by hook:
- **Elimination (mode 6):** continues and wins per player; the Shell's two `m_continues` are 0 or 1 during
  `StateDeath::transitionInto` and `StateVictory::transitionOK` (it ends only when one is left). Death with a continue: retail dialog 8 for
  that player (`m_won[1]`), `SetPlayerMonster` and `playerInit`; the dialogs are modal and return through a trampoline
  (`EvaluateOnlineBattleStatus + 4`, which the game never executes) that does the rest and resumes `EvaluateGameStatus`, also when the thread
  yielded in the middle. Without a continue and with more than one in the fight: the player leaves (monster hidden, their camera follows whoever goes on). One
  left: dialog 0xB; "play again" puts players 3 and 4 back on their starting monster. Selection: costume 0, exclusive monster.
- **Dodgeball (7):** hits of players 3 and 4 outside `DodgeBallLevel` (the retail counter has 2 and the 3rd would write into the ball's
  count); "P3"/"P4" in views 2 and 3. The arena only has 2 start points: the extra player spawns at the point rotated 90° around their
  center (`wotm_split4.inc`).
- **Crush (9):** 4-way scoreboard, winner by the highest of the 4 `TokenManager`, a tie at the top goes to sudden death with everyone; the camera frames
  the farthest pair.
- **Big Shot (8):** rotation in the 2 seats of `BigShotLevel` (3 turns per player); in the last one, the two best in the seats for the
  retail comparison (tie: "king of the hill" between them) and the others standing still at the waiting point.
- Minigame end dialogs with "Player 3/4 - scored".

## Campaign with up to 4 players (`wotm_coop.inc`)
The adventure (mode 1) with 2 to 4 players is the Shell's mode 1 with `m_numPlayers` from 2 to 4; there is no flag of its own. Retail's 1-player
one stays as it was.
- **Entry:** ADVENTURE row in the screen 5 list, after the controller selection (`wotm_mainmenu.inc`, `kAdventureRow`).
  `adventureStart` (`wotm_padsel.inc`) sets mode 1, stage 1, no AIs in the selection, zeroes the accumulated score and the save mark, and opens
  screen 6: with 2 players the retail selection, with 3 and 4 (or 2 with a bot) the big screen one without CPUs. On exit from the selection, `6 → 8` becomes `6 → 0x63` (straight to the
  load) with the stage AIs copied again (`adventureAis`); going back from 6 leads to the list on 5.
- **Screen:** `gameReestablishViews` runs with `m_gameMode` 3 during the call: with 2 players the retail halves, with 3 and 4 the
  quadrants of `wotm_split4.inc` (`splitPlayers` accepts mode 1). No unified view (the close combat camera would join two
  allies): everyone's `m_camUnify` stays at 0 every frame.
- **Screen with whoever is left:** when a player leaves, view v shows the v-th one still going: camera v follows them
  (`SetCameraToFollowMonster` writes `m_cameraView = v`, and the controls and HUD messages go along) and `m_viewSlot[v]` is theirs.
  1 player: full screen; 2: halves; 3: the split4 3-player layout. `applyLayout`, at the start of each frame, rebuilds the cameras and views
  that the cinematic, the toggle or `playerInit` undid. During `Hud::update`, `m_numMonsters` is the number of views (1 or 2:
  bar position), `m_monsters` come in view order and whoever left has `m_playerNum` 0 (`addHealthIndicators` does not
